# Сборка UI Type Rail

Собери законченный Rail по концепту на всех запрошенных платформах. Полный охват: пять фиксированных устройств iOS, три Android-макета и шесть Web-брейкпойнтов, включая Desktop. При явно ограниченном запросе выполняй выбранный поднабор. Grid использует собственные правила раскладки.

## Что читать

- Всегда: [общие правила](references/common.md), [собственная карточка UI Type](references/card-component.md) и [проверка на устройствах](references/device-review.md).
- Для выбора радиуса новых карточек: [шкала по минимальной стороне и аудит](references/radius.md). Это beta-политика, существующие утверждённые радиусы не пересчитываются автоматически.
- Для нового концепта любой детализации: [разбор концепта и контракт сборки](references/concept.md). При полном запросе результат содержит 14 геометрических вариантов в трёх платформенных наборах; дополнительные состояния не заменяют это покрытие.
- Только нужные платформы: [iOS](references/ios.md), [Android](references/android.md), [Web](references/web.md). У платформ разные модели расчёта; одной универсальной формулы нет.
- Для продолжения работы с существующей библиотекой: [карта мастеров и состояние](references/current-library.md). Карта актуализирована 17 ноября 2026, перед изменениями проверь живые узлы.
- Для изменения слотов или Shape=Custom: [механика Figma](references/figma-mechanics.md).
- Для сеток: соседний навык [rail-layout-guides](../rail-layout-guides/SKILL.md).
- Для старых измерений конкретного семейства: [Web](references/source-web-sizing.md), [Android](references/source-android-sizing.md). Данные от 11 ноября описывают исходники, а не текущую готовность новой библиотеки.

Используй доступные официальные Figma-инструменты. Перед выполнением JavaScript в файле прочитай применимые инструкции figma-use, а перед изменением компонентов — figma-generate-library. Сведения этого навыка не заменяют документацию текущего API.

## Работа в фича-макете и перенос в библиотеку

По умолчанию собирай Rail в текущем фича-файле рядом с концептом или в указанной дизайнером области. Подключённая UI Type — источник опубликованных Rail Card, Rail Heading, Rail Example, запчастей, переменных и Guidelines. Наличие концепта в продуктовом файле не требует переноса работы в библиотеку.

1. Проверь реальные опубликованные зависимости, доступные через подключённую UI Type. Rail Card импортируй как шаблон для самостоятельной карточки UI Type: detach только внешнего экземпляра, затем собственный мастер с вариантами размеров. Heading, платформенные базы и совместимые запчасти сохраняй связанными. Внутри библиотеки используй доступные локальные мастера. Не отвязывай базы ради обхода недоступной зависимости. Если транзитивная зависимость доступна через экземпляр, дополнительное подключение платформенной библиотеки не требуется. Если для нового элемента нужен недоступный мастер, назови конкретную библиотеку и продолжай независимую работу.
2. Используй существующий UI Type или экземпляр Rail Example как отправную точку. Внешний экземпляр Rail Example разрешено detach. Для карточки используй собственный мастер UI Type без вложенной универсальной Rail Card, с восстановленными boolean-свойствами и обычными FRAME Overlay/Caption. Heading и вложенные платформенные базы сохраняют связи. Создай локальный Rail, набор карточек по размерам и только необходимые запчасти. Исходный библиотечный мастер не меняй ради фичи.
3. Выполни запрошенный платформенный охват. Например, запрос «Web» означает шесть Web-брейкпойнтов, без автоматической сборки iOS и Android. Для общего запроса без указания платформ сохраняется полный охват 5/3/6. Подготовь проверку в этом же фича-файле.
4. Дизайнер дорабатывает композицию, содержимое и размеры локального Rail. При повторном запуске сохраняй его изменения и исправляй только запрошенное. Связи с библиотечными базами и привязки переменных сохраняются.
5. По отдельному запросу перенеси согласованный UI Type в библиотеку и адаптируй под оставшиеся платформы. Перед переносом проверь конфликты имён, существующие мастера, запчасти и ссылки из фича-файла. Переноси Rail и уникальные запчасти вместе через поддерживаемый Figma перенос компонентов между файлами, сохраняя идентичность и связи. Если такой перенос недоступен инструменту, укажи нужное ручное действие, а не создавай молча дубликат. После переноса проверь собственные мастера карточек, вложенные зависимости, boolean-связи, темы, сохранённые исходные слоты (если есть) и экземпляры исходного файла. Публикация и обновление экземпляров — отдельные явные действия, статус каждого сообщай.

Текущий навык собирает Rail. Для работы с существующими Android Grid открой [базу знаний Grid](../../../design-system/components/grid-android-ui-type.md) и сверяй конкретный мастер в указанном файле или ветке. TV использует отдельную библиотеку и свои правила.

## Рабочий проход

1. Разбери концепт по contract reference: намерение, повторяемая единица, состав, пропорции и адаптация. Найди целевой тип, исходник, текущие локальные Rail Card нужной платформы, общий Rail Heading и подходящие запчасти. Разреши фактические зависимости, не выбирай мастер по одному имени.
2. При переносе проверь каждую карточку каждого исходного варианта: вложенности, переопределения и все скрытые слои. Сохрани исходную видимость, индивидуальный контент и свойства; сопоставь их слоям собственного мастера. Сохраняемые исходные SLOT проверяй отдельно от FRAME новой карточки.
3. Выбери платформенный шаблон стандартной Rail Card/Custom или кастомную композицию; создай собственный мастер карточки по card-component.md. В карусели должны быть его экземпляры. Восстанови семь применимых boolean-связей; слоты по умолчанию не добавляй. Нестандартная пропорция больше не является причиной пропускать UI Type. WIP исключён из переноса, если пользователь не расширил задачу.
4. Определи геометрию отдельно для каждой платформы. На iOS сохраняй утверждённые фиксированные размеры, JSON используй для проверки. На Android используй сетку и подтверждённые исключения. На Web запиши S, L, R, N, G и применимость модели конкретному типу.
5. Собери варианты Rail, собственных карточек, шапку, карусель, FRAME Overlay/Caption и запчасти. При сборке по концепту на каждую обложку всегда ставь дефолтную картинку-плейсхолдер из библиотеки по общим правилам, на всех платформах. Внутренние padding и gap карточки привяжи к семантическим `spacing/*` из Tokens Web&Mobile. Сохрани связи с платформенными базовыми компонентами и переменными. Не создавай новых токенов, коллекций или переменных; импорт существующих разрешён.
6. Используй имена `Rail <тип> 🍎 iOS`, `Rail <тип> 🤖 Android`, `Rail <тип> 🌐 Web`. Размести их в ряд на странице `<тип> Rail`; мастера без секций-обёрток, запчасти рядом. Не создавай дубли только из-за ширины.
7. Заверши сборку и подготовь отдельные проверочные секции на устройствах с включёнными локальными сетками по device-review.md. Общий Preview без экранных фреймов не создавай. Проверь размеры обложек отдельно от подписей, gap, радиусы и темы, зависимости, скрытый контент, семь переключателей, повторное наследование ширины и внутренних правок от мастера карточки; исключи непреднамеренные width/height overrides. Покажи все обязательные устройства; найденные ошибки сообщай дизайнеру без автоматического исправления.

У Carousel задавай `clipsContent=false`; переполнение ограничивает экранный фрейм проверки. Не экспонируй Heading, карточки и другие внутренние экземпляры в Nested instances конечного Rail без явного запроса. Все запчасти публикуй в группе `x / ` без скрывающего `_`; для наполнения слота сохраняй `Slot` в имени, например x / Rail Media Slot Overlay Phone.

При добавлении UI Type в основную библиотеку обнови каталог UI Type на странице Structure (2300:26048). Добавь одну плитку на тип с узнаваемым связанным экземпляром карточки одной платформы и ссылкой на актуальный мастер в этой библиотеке. При добавлении платформы к существующему типу переиспользуй плитку. Для похожих карточек можно подписать отличие композиции, например число рядов.

## Результат

Дай ссылки на готовые узлы, перечень вариантов, результат проверки и точные оставшиеся ограничения. Не объявляй непроверенные токены или скрытые слои готовыми. При неизвестных деталях продолжай независимую понятную работу, вопросы по оставшимся пунктам собери в конце, если пользователь не указал иной порядок. Не публикуй библиотеку и не изменяй исходные платформенные Rail без отдельного указания.
