# Принципы сборки Rail Web

> Актуальная архитектура новых сборок: [собственная карточка UI Type](card-component.md). Rail Card/Custom ниже описывают шаблон и его геометрию. В Carousel используется самостоятельный мастер без вложенной универсальной Rail Card, с FRAME Overlay/Caption и восстановленными переключателями. Настоящие SLOT сохраняются при точном переносе существующего компонента или явном запросе; исторические примеры не отменяют это разделение.


Рабочая редакция от 13 ноября 2026 года. Основана на решениях из чата, текущих компонентах библиотеки UI Type и проверенных токенах. Документ описывает правила сборки; он не означает, что все исторические компоненты уже полностью им соответствуют.

## 1. Rail — готовая композиция UI Type

Rail включает заголовок, карусель и её содержимое. По концепту могут добавляться навигация, фон, спонсорский блок и другие элементы.

Повторяемой единицей может быть отдельная карточка или колонка из нескольких карточек. Это нужно определить до расчёта размеров. У двухрядного Rail горизонтальное количество N относится к колонкам; вертикальные интервалы рассчитываются отдельно.

Исходный концепт задаёт содержание, композицию, поведение и плотность карточек. При воспроизведении существующего типа проверяются все исходные карточки, включая скрытые слои и индивидуальные переопределения.

## 2. Выбор карточки

Предусмотрены три подхода.

| Подход | Когда применять |
|---|---|
| Rail Card Web, стандартный Shape | Подходит общая структура карточки и одно из стандартных соотношений сторон |
| Rail Card Web, Shape=Custom | Подходит общая структура, нужны произвольные пропорции обложки |
| Полностью кастомная карточка | Самостоятельная композиция или поведение, которые не укладываются в Rail Card |

У стандартной Rail Card доступны Horizontal 16:9, Vertical 2:3, Square 1:1 и Circle 1:1. Соотношение относится к обложке, а не к карточке вместе с подписью.

Для Shape=Custom ширина и общая высота экземпляра независимы. При включённой подписи обложка занимает оставшееся место: высота обложки = общая высота карточки − высота области подписи − применимые промежутки и отступы. Если концепт задаёт обложку 4:5, сначала рассчитывается её высота по этой пропорции, затем добавляется подпись.

У кастомной карточки разрешены собственные пропорции. Нестандартное соотношение сторон не является основанием исключать UI Type из сборки. Мастер кастомной карточки хранится в библиотеке UI Type рядом с соответствующим Rail.

## 3. Источники компонентов

- Rail Card Web и Rail Heading берутся из библиотеки UI Type.
- Label, Rich Label, кнопки и другие базовые компоненты берутся из Lib-Web или подтверждённой общей базовой библиотеки.
- Уникальные запчасти конкретного Rail создаются в библиотеке UI Type.
- Совместимые общие запчасти переиспользуются между типами и платформами. Разница только в ширине не требует нового мастера.
- При переиспользовании проверяются состав, типографика, токены, состояния и библиотечные зависимости.
- Экземпляры сохраняют связь с мастерами. Базовые компоненты не заменяются нарисованными копиями.

## 4. Обязательные брейкпойнты

Для полной Web-сборки нужен один компонентный набор с шестью вариантами свойства breakpoint: 320, 375, 768, 1024, 1440 и 1920. Web включает мобильные, планшетные и десктопные размеры.

| Брейкпойнт, px | Device карточки и шапки | Screen padding L, px | Правый расчётный R, px | Gap G, px | Токен интервала |
|---:|---|---:|---:|---:|---|
| 320 | Phone | 12 | 36 | 6 | rail/gap-horizontal/phone |
| 375 | Phone | 12 | 36 | 6 | rail/gap-horizontal/phone |
| 768 | Tablet | 32 | 56 | 8 | rail/gap-horizontal/tablet |
| 1024 | Tablet | 32 | 56 | 8 | rail/gap-horizontal/tablet |
| 1440 | Desktop | 56 | 56 | 8 | rail/gap-horizontal/tablet |
| 1920 | Desktop | 72 | 72 | 10 | rail/gap-horizontal/desktop |

Screen padding соответствует отдельным Web-токенам:
- 320/375 — screen-padding/web/mobile;
- 768/1024 — screen-padding/web/tablet;
- 1440 — screen-padding/web/desktop-m;
- 1920 — screen-padding/web/desktop-l.

Device и токен интервала выбираются отдельно. На 1440 Device=Desktop, а gap=8 через tablet-токен. Слово Desktop само по себе не означает gap=10.

L и G подтверждены токенами и текущим Rail Main Web. Значения R восстановлены по геометрии стандартных семейств; отдельный Web Technical-токен R в проверенных источниках не найден. Это рабочая таблица стандартных Rail. Особую геометрию конкретного концепта, включая Highlights и Announces, нужно описывать отдельно.

Для построения доступны нативные Layout guide styles: Web/Mobile (320, 375) — общий для 320, 375 и других Mobile-ширин с теми же параметрами; Web/Tablet (768, 1024) — общий для 768 и 1024; Web/Desktop M (1440) — для 1440; Web/Desktop L (1920) — для 1920. Над Web-примерами дополнительно указаны подписи breakpoint=320, breakpoint=375, breakpoint=768, breakpoint=1024, breakpoint=1440 и breakpoint=1920. Desktop разделён из-за различий padding и gap. Стиль применяется к фрейму полной ширины экрана, а не к уже уменьшенной полезной области Rail. Колонки растягиваются вместе с фреймом. Показаны 12 вспомогательных колонок и красная полоса полного правого расчётного отступа R; число колонок guides не заменяет расчёт карточек через N.

Шесть размеров являются опорными макетами. Они сами по себе не определяют все правила между ними: границы переключения типографики, токенов и плотности должны быть заданы правилами адаптивности конкретного Rail. Layout guide style не переключается между группами автоматически при ресайзе.

## 5. Три разные ширины

S — ширина экрана или согласованного внешнего контейнера. В примерах ниже используется ширина экрана.

Для стандартного Rail:
- L — левый screen padding;
- P — обычный правый screen padding, равный L;
- R — полный правый расчётный отступ от края экрана;
- B = S − L − P — видимая ширина Rail;
- A = S − L − R — область, по которой рассчитывается ширина карточек.

На мобильных и планшетных макетах R больше screen padding на 24 px. На 1440 и 1920 R равен screen padding.

R уже включает отступ от края экрана. К нему не нужно повторно прибавлять screen padding. R также не следует автоматически назначать как paddingRight карусели.

Например, на 375:
- ширина экрана S = 375;
- видимая ширина Rail B = 375 − 12 − 12 = 351;
- расчётная область A = 375 − 12 − 36 = 327.

Заголовок и видимая область карусели здесь имеют ширину 351. Карточки рассчитываются по области 327. Эти две области не нужно уравнивать.

У Rail с фоном или сложной композицией внешний корень может иметь другую ширину. Отступы нельзя вычитать повторно, если родитель уже ограничил полезную область.

## 6. Формула ширины карточки

W = (S − L − R − ((N − 1) × G)) / N

Где:
- W — ширина повторяемой карточки или колонки;
- S — ширина экрана;
- L — левый screen padding;
- R — полный правый расчётный отступ;
- G — интервал между карточками;
- N — расчётное количество карточек или колонок в области A.

Сначала из ширины экрана вычитаются левый и правый расчётные отступы. Затем вычитаются промежутки: (N − 1) × G. Остаток делится на N.

N задаётся отдельно для каждого типа и брейкпойнта до расчёта W. Не подгоняй N обратной формулой под пиксельную ширину концепта ради видимости правильного расчёта; если плотность не задана и не подтверждена подходящим семейством, уточни её у дизайнера. Оно может быть дробным. Для текущих стандартных Web-семейств используется непрерывная формула N − 1, без ceil и без переноса правила iOS. При дробном N это расчётный коэффициент плотности, а не обещание буквального количества видимых карточек на всём экране.

Пример Rail Main на 1024:
W = (1024 − 32 − 56 − ((4 − 1) × 8)) / 4 = 228 px.

Пример текущего Rail Main на 375:
N = 5/3;
W = (375 − 12 − 36 − (((5/3) − 1) × 6)) / (5/3) = 193,8 px.

Эти значения N подтверждают геометрию Main и не становятся общими значениями для всех Rail.

Сохраняется точность вычисления. Для показа результата допустимо округление до двух знаков; промежуточные вычисления и дробное N не округляются автоматически до целых.

Для сложной кастомной композиции сначала определяется ширина повторяемого блока. Размер вложенного изображения не следует автоматически принимать за ширину карточки.

## 7. Высота карточки и Rail

Для стандартных пропорций:
- Horizontal: высота обложки = W × 9/16;
- Vertical: высота обложки = W × 3/2;
- Square и Circle: высота обложки = W.

Подпись и её отступы добавляются отдельно. Высота шапки не входит в высоту карточки.

У Rail высота складывается из видимых элементов композиции: шапки, интервала до карусели, высоты карусели и дополнительных блоков. Скрытая шапка не должна оставлять пустой промежуток.

В двухрядном типе учитываются высота обеих карточек, их подписи и вертикальный интервал. Горизонтальный gap не используется вместо вертикального автоматически.

## 8. Сборка в Figma

Основной каркас — Rail Heading и Carousel внутри вертикального Auto Layout. Внутри карусели карточки или колонки располагаются горизонтально.

- Заголовок растягивается по ширине Rail.
- Карточки получают рассчитанную ширину. Fill у всех карточек не должен распределять ширину между всем списком и менять заданную плотность.
- Высота контейнеров учитывает подписи и изменение текста.
- У Carousel `clipsContent=false`; переполнение ограничивает внешний экранный фрейм проверки. Clipping обложки сохраняется независимо.
- Оверлеи привязываются к обложке, а подпись находится под ней.
- Для изображения сохраняется технический слой Cover.
- Overlay/Caption новой карточки — FRAME; слоты сохранённых исходников используются по назначению.
- Состояние Skeleton берётся из Rail Card; отдельные дубли скелетона для обычной Rail Card не создаются.
- Лишние Base Rail и одноэлементные обёртки не добавляются. Контейнеры рядов и колонок сохраняются, когда у них есть функция.

В Figma ширины карточек на опорных брейкпойнтах задаются расчётом. Наличие Auto Layout не означает, что формула N уже автоматически выполняется при произвольном ресайзе. Адаптивный пересчёт для разработки описывается явно.

## 9. Шапка и навигация

Используется общий компонент Rail Heading с Type=Base или Rich и подходящим Device.

Для Phone и Tablet сохраняются общие платформенные варианты шапки. Для Desktop используется его собственный размер типографики и изображений; правая стрелка перехода в шапке скрыта.

Стрелка шапки и управление прокруткой карусели — разные элементы. Скрытая стрелка Desktop-шапки не означает удаление кнопок навигации карусели.

Навигация, изображения и дополнительные блоки подключаются по концепту из существующих компонентов. Собственные копии базовых иконок и кнопок не рисуются.

## 10. Токены

Интервалы между карточками привязываются к локальным rail/gap-horizontal/* в библиотеке UI Type. Значение назначенного токена должно совпадать с G в формуле.

Для карточек Rail выбираются только скругления, предусмотренные системой Rail Card. Они привязаны к переменным rail/card/radius/* и могут менять значение в зависимости от темы. Выбор скругления означает выбор соответствующего компонентного токена, а не копирование его текущего числового значения.

У экземпляров Rail Card сохраняются привязки мастера. У Shape=Custom и полностью кастомных карточек используется та же система скруглений Rail Card; произвольные значения и сторонние radius-токены не назначаются. При переключении темы скругления должны обновляться через переменные без ручной правки каждого Rail. У формы Circle сохраняется круглая геометрия мастера. Вложенные кнопки и лейблы сохраняют собственные платформенные токены.

Screen padding берётся из Web-семейства, а не из iOS или Android.

Внутренние padding и gap карточки привязывай к семантическим переменным `spacing/*` из Tokens Web&Mobile по [общим правилам](common.md).

## 11. Имена и организация библиотеки

- Страница: `<тип> Rail`.
- Компонент Web: Rail <тип> 🌐 Web, например Rail Main 🌐 Web.
- Варианты: breakpoint=320, breakpoint=375 и остальные согласованные значения.
- Запчасть: x / Rail <тип> <роль> [платформа] [размер], например x / Rail Continue Slot Caption Web Desktop L.
- Общая запчасть не получает платформенный суффикс без необходимости.

Основные компоненты доступны прямо на странице. Секции и дополнительные контейнеры вокруг мастеров не используются. Порядок платформ слева направо: iOS, Android, Web. Запчасти находятся рядом с соответствующим компонентом, общие — в одном экземпляре. Проверку размещай в отдельных платформенных секциях с экранными фреймами по [device-review.md](device-review.md). Запрет секций-обёрток относится к мастерам.

Rail — название типа композиции. Общий префикс UI Type не добавляется: у Grid своё название.

## 12. Проверка готовности

Следуй [проверке на устройствах](device-review.md): покажи связанные экземпляры на всех обязательных экранах с включёнными локальными сетками. Ошибки сообщай дизайнеру без автоматического исправления.

Rail Web готов к передаче, когда:

1. Собраны все шесть брейкпойнтов; любое исключение описано явно.
2. Для каждого варианта записаны S, L, R, G, N, ширина и пропорции обложки.
3. Выбран правильный подход: стандартная Rail Card, Custom или кастомная карточка.
4. Сохранились связи с мастерами, базовыми компонентами, стилями и переменными. Скругления карточек взяты только из системы Rail Card; их привязки сохранены и изменение при переключении темы проверено.
5. Проверены все карточки, скрытые слои, состояния, содержимое обоих слотов и индивидуальные переопределения.
6. Лейблы, оверлеи, скелетон и подписи работают при изменении размеров.
7. Нет случайной обрезки текста и наложений; намеренные обрезка и сокращение текста соответствуют концепту.
8. Проверены шапка Desktop, навигация, внешний вид и доступная область карусели.
9. Соблюдены нейминг, плоская структура мастеров и расположение запчастей.
10. Предположения, исключения и неподтверждённые токены перечислены отдельно.
