# Принципы сборки Rail iOS

Рабочая редакция от 13 ноября 2026 года. Документ основан на решениях из чата, текущей библиотеке UI Type и проверенном Technical(iOS) JSON. Правила сборки отделены от исторических размеров и известных расхождений.

Основное правило iOS: сохраняются утверждённые фиксированные размеры карточек для каждого устройства. Technical JSON используется для проверки и объяснения размеров. Расхождение с формулой или фактической шириной экранного макета само по себе не является основанием для пересчёта.

## 1. Состав Rail и исходный концепт

Rail — готовая композиция UI Type: общий заголовок, карусель и карточки. Фон, изображения, спонсорские и другие блоки подключаются по концепту.

До сборки определяются повторяемая единица, число рядов, содержание карточек, пропорции обложек, подписи и состояния. Повторяемой единицей может быть отдельная карточка или колонка из нескольких карточек.

При воспроизведении существующего типа проверяются все исходные карточки, включая скрытые слои и индивидуальные переопределения. Одного названия типа недостаточно для выбора геометрии и состава.

## 2. Источники компонентов

- Карточка — локальный Rail Card iOS из библиотеки UI Type.
- Заголовок — общий Rail Heading из этой же библиотеки.
- Label, Rich Label, кнопки и другие базовые компоненты — из Lib-iOS или подтверждённой общей базовой библиотеки.
- Уникальные запчасти создаются в библиотеке UI Type рядом с соответствующим Rail.
- Совместимые подписи, оверлеи и другие запчасти переиспользуются между типами и платформами. Разница только в ширине не требует нового мастера.
- При переиспользовании проверяются состав, свойства, типографика, токены, состояния и базовые зависимости.

Экземпляры сохраняют связи с мастерами. Базовые компоненты не заменяются нарисованными копиями. Правки Lib-iOS не входят в обычную сборку Rail в библиотеке UI Type.

## 3. Пять обязательных фиксированных макетов

| Вариант Rail | Размер экранного макета, px | Ориентация | Device карточки и шапки | Screen padding P, px | Обычная полезная ширина B, px |
|---|---|---|---|---:|---:|
| Device=iPhone 15 | 393 × 852 | Portrait | Phone | 15 | 363 |
| Device=iPhone 17 Pro Max | 440 × 956 | Portrait | Phone | 15 | 410 |
| Device=iPad Mini 6 | 1133 × 744 | Landscape | Tablet | 35 | 1063 |
| Device=iPad 10 | 1180 × 820 | Landscape | Tablet | 35 | 1110 |
| Device=iPad Pro 13 | 1376 × 1032 | Landscape | Tablet | 35 | 1306 |

Для iOS собираются пять фиксированных вариантов конкретных устройств. Один общий Phone и один общий Tablet не заменяют эти макеты. Внутренняя Rail Card и совместимые запчасти могут иметь только Phone/Tablet и получать нужный размер в экземпляре.

В библиотеке есть дополнительные шаблоны iPhone 13 mini и портретных iPad. Они не расширяют обязательный набор автоматически. Пометка Optional у экранного шаблона iPad Mini не исключает его из подтверждённого набора Rail.

Для обычной полезной области B = ширина экранного макета − 2 × P. У фонового или составного Rail внешний корень может иметь полную ширину экрана. Перед назначением отступов проверяется, не ограничил ли родитель полезную область.

## 4. Платформенные отступы и интервал

| Группа | Левый screen padding L, px | Правый расчётный R из Technical(iOS), px | Gap G, px | Токен интервала |
|---|---:|---:|---:|---|
| iPhone | 15 | 30 | 6 | rail/gap-horizontal/phone |
| iPad | 35 | 50 | 8 | rail/gap-horizontal/tablet |

Screen padding берётся из screen-padding/ios/iphone и screen-padding/ios/ipad.

R — полный правый расчётный отступ от края расчётной области. Он уже включает свою величину целиком: screen padding повторно к нему не прибавляется.

R используется в формуле размера карточки. Он не назначается автоматически как paddingRight карусели, не считается safe area и не вычитается повторно из уже рассчитанной ширины.

Фактический gap между карточками привязывается к локальным переменным rail/gap-horizontal/* из библиотеки UI Type. В формуле используется значение того же токена.

## 5. Формула ширины карточки iOS

Формула применяется как проверочный расчёт. Утверждённый фиксированный размер карточки имеет приоритет перед полученным результатом. Для нового типа формула помогает подготовить размеры к утверждению; она не отменяет отдельную фиксацию итоговой геометрии.

Ширина карточки = (расчётная ширина − левый screen padding − правый расчётный отступ − (количество промежутков × gap)) / ожидаемое количество карточек.

Количество промежутков = ожидаемое количество карточек, округлённое вверх, минус 1; минимум 0.

Обозначения для агента:

A = S − L − R
K = max(0, ceil(N) − 1)
W = (A − K × G) / N

Где:
- S — подтверждённая входная ширина для расчёта;
- A — расчётная область;
- L — левый screen padding;
- R — правый расчётный отступ;
- N — ожидаемое количество карточек или колонок в расчётной области;
- K — количество промежутков;
- G — интервал между карточками;
- W — ширина повторяемой карточки или колонки.

N задаётся для конкретного типа и устройства и может быть дробным. Например:
- N=1,5 → K=1;
- N=2,5 → K=2;
- N=3 → K=2.

Это iOS-правило. Web-формула с непрерывным N−1 сюда автоматически не переносится. Android использует свою сеточную модель.

N не означает количество экземпляров, которое нужно создать в карусели. Для двухрядного Rail горизонтальное N относится к колонкам; высота и вертикальные интервалы считаются отдельно.

N должно быть больше 0, расчётная область и полученная ширина — положительными. Промежуточные вычисления и дробное N не округляются произвольно.

## 6. Входная ширина S и действующие фиксированные размеры

Нужно различать:
1. фактическую ширину экранного макета;
2. полезную ширину Rail B;
3. входную ширину S выбранного расчёта;
4. полученную или утверждённую ширину карточки W.

В историческом Technical JSON S может отличаться от актуального экранного шаблона. Пользователь уточнил причину для среднего iPhone: во время редизайна Rail расчёт выполнялся по ширине 390 px; текущий экранный макет имеет ширину 393 px. Поэтому карточка Main 226 px соответствует исходной базе 390 и сохраняется как утверждённый фиксированный размер. Это объяснённое различие расчётной базы и экранного макета, а не основание автоматически исправлять карточку.

Историческую базу нельзя выдавать за фактическую ширину нового экрана. Совпадение имени устройства также не доказывает, что все входные данные уже обновлены.

Текущий Rail Main iOS имеет следующие размеры:

| Устройство | Фактическая ширина экранного макета, px | Текущая ширина карточки W, px | База S исторического Technical JSON, которая воспроизводит W | N Main в этом наборе |
|---|---:|---:|---:|---:|
| iPhone 15 | 393 | 226 | 390 — iPhone Regular | 1,5 |
| iPhone 17 Pro Max | 440 | 259,333… | 440 — iPhone Wide | 1,5 |
| iPad Mini 6 | 1133 | 214,333… | 744 — iPad Compact | 3 |
| iPad 10 | 1180 | 222,333… | 768 — iPad Regular | 3 |
| iPad Pro 13 | 1376 | 249,8 | 1366 — iPad Wide | 5 |

Связь с исторической базой здесь подтверждается совпадением вычисленных размеров. Таблица описывает текущие макеты и не устанавливает универсальную новую привязку устройств к Technical-наборам.

Исторический пример iPhone Regular:
W = (390 − 15 − 30 − 1 × 6) / 1,5 = 226 px.

Если для нового расчёта явно использовать фактическую ширину iPhone 15:
W = (393 − 15 − 30 − 1 × 6) / 1,5 = 228 px.

Это два разных набора входных данных. Нельзя назвать одновременно 226 и 228 одним и тем же результатом для одинакового S.

Подтверждённое решение: сохранять утверждённые фиксированные размеры карточек, JSON использовать для проверки. Для iPhone 15 в текущем Main сохраняется 226 px; проверочный результат 228 px не заменяет этот размер автоматически. То же правило действует для остальных устройств и типов.

Для нового типа фиксированные размеры определяются концептом и утверждаются по каждому устройству. Для пересборки существующего типа сохраняются его утверждённые значения. Изменение размеров является отдельной явно поставленной задачей, а найденные расхождения записываются без автоматической правки макета.

## 7. Technical JSON как источник проверки

Проверенные наборы находятся в themes/Technical(iOS)/Ui Type/:
- iPhone Compact 0-320;
- iPhone Regular 321-413;
- iPhone Wide 414+;
- iPad Compact 0-767;
- iPad Regular 768+;
- iPad Wide 1024+.

Сопоставление параметров:
- S — container.device-width либо отдельно подтверждённая входная ширина;
- L — screen-padding.left;
- R — screen-padding.right;
- N — cover.numbers.<type>;
- K — cover.gaps-count.<type>;
- W — cover.width.<type>;
- высота обложки — cover.height.<type>, с проверкой пропорции и правил округления.

Диапазоны в названиях файлов не заменяют проверку устройства, ориентации и входных данных. Платформенный набор выбирается по подтверждённому соответствию, а не только по совпадению числа в имени.

В старом JSON есть исключения и ошибки: Medium у iPhone Regular/Wide использует дополнительное gaps-count−1, а отдельная ссылка square-medium ведёт к отсутствующей высоте. Такие особенности не распространяются на все Rail и не исправляются молча в репозитории. При влиянии на результат расхождение фиксируется и разрешается отдельно.

Layout guides помогают визуальной проверке. Они не заменяют формулу и не доказывают правильность размеров всех iOS-карточек.

## 8. Выбор карточки и пропорций

| Подход | Когда применять |
|---|---|
| Rail Card iOS со стандартным Shape | Подходят общая структура и стандартная пропорция |
| Rail Card iOS, Shape=Custom | Подходит структура, нужны произвольные пропорции обложки |
| Полностью кастомная карточка | Нужны собственная структура или поведение |

Стандартные формы обложки: Horizontal 16:9, Vertical 2:3, Square 1:1 и Circle 1:1.

Для стандартной обложки:
- Horizontal: H = W × 9/16;
- Vertical: H = W × 3/2;
- Square и Circle: H = W.

Подпись, её отступы и дополнительные строки добавляются отдельно. Высота шапки не включается в размер карточки.

Rail Card сохраняет точную пропорцию обложки. В историческом Technical JSON для некоторых высот есть ceil; это отдельное правило округления источника. Оно не применяется автоматически так, чтобы нарушить пропорцию действующего мастера.

Shape=Custom позволяет независимо менять ширину и общую высоту экземпляра. При включённой подписи обложка занимает пространство за вычетом подписи и применимых отступов. Если концепт задаёт собственную пропорцию обложки, сначала рассчитывается её высота, затем добавляется область подписи.

Полностью кастомная карточка может иметь собственные пропорции. Она создаётся локально в UI Type с переиспользованием подходящих платформенных баз и общих запчастей. Нестандартное соотношение сторон само по себе не является причиной откладывать UI Type.

## 9. Скругления и тема

Для карточек Rail выбираются только скругления из системы Rail Card. Используются предусмотренные переменные rail/card/radius/*, которые получают значение активной темы.

У экземпляров сохраняются привязки мастера. У Shape=Custom и полностью кастомных карточек используется та же система скруглений Rail Card. Значение токена не копируется как фиксированное число.

Произвольные скругления и сторонние radius-токены для карточки не назначаются. При переключении темы проверяется соответствие скруглений её переменным. Circle сохраняет круглую геометрию мастера. Базовые кнопки и лейблы внутри сохраняют собственные платформенные токены.

Внутренние padding/gap карточки отличаются от промежутков карусели. Точный путь отдельного семейства Rail Card Padding Gap пока не подтверждён. У проверенного мастера Labels / padding содержит числовые 6 и 2 без привязок. До уточнения сохраняются настройки мастера; rail/gap-horizontal/* не используется вместо внутреннего токена. Незавершённая токенизация отмечается явно.

## 10. Сборка, слоты и шапка

Основной каркас — Rail Heading и Carousel внутри вертикального Auto Layout. Внутри Carousel карточки или колонки располагаются горизонтально.

Шапка и видимая область карусели используют доступную ширину, карточки — утверждённую фиксированную ширину конкретного устройства. Fill у всех карточек не должен распределять ширину между всем списком и менять плотность.

Rail Heading используется с Type=Base или Rich и подходящим Device=Phone/Tablet. Эти варианты общие для платформ. При скрытой шапке лишний промежуток до карусели не остаётся. Desktop-вариант для iOS не создаётся.

Оверлеи помещаются в слот элементов обложки, подпись — в слот подписи. Сохраняется технический слой изображения Cover. Проверяются позиции лейблов и оверлеев относительно краёв обложки.

Для обычной Rail Card используется встроенное состояние Skeleton. Дублирующие мастера скелетона не создаются. У кастомной карточки состояние загрузки определяется её композицией с переиспользованием подходящих базовых компонентов.

Высота Rail учитывает видимые элементы: шапку, интервалы, карточки, подписи и дополнительные блоки. Лишние Base Rail и одноэлементные обёртки не добавляются. Контейнеры рядов и колонок сохраняются, когда у них есть функция.

## 11. Имена и организация

- Страница: Rail <тип>.
- Компонент: Rail <тип> iOS, например Rail Main iOS.
- Варианты: пять конкретных Device из обязательного перечня.
- Запчасть: x / Rail <тип> <роль> [платформа] [размер].
- Совместимая общая запчасть не получает суффикс iOS только из-за происхождения.

Мастера лежат непосредственно на странице. Секции и дополнительные контейнеры вокруг мастеров не используются. Порядок платформ — iOS → Android → Web. Запчасти располагаются рядом с компонентом, общие сохраняются в одном экземпляре. Проверку размещай в отдельных платформенных секциях с экранными фреймами по [device-review.md](device-review.md). Запрет секций-обёрток относится к мастерам.

## 12. Проверка готовности

Следуй [проверке на устройствах](device-review.md): покажи связанные экземпляры на всех обязательных экранах с включёнными локальными сетками. Ошибки сообщай дизайнеру без автоматического исправления.

1. Есть все пять обязательных устройств, сохранены размеры и ориентации экранных макетов.
2. Для каждого варианта записаны утверждённый фиксированный размер карточки и его источник. При проверке по JSON отдельно записаны фактическая ширина экрана, полезная область, входная ширина S, Technical-набор, L, R, N, K, G и проверочный результат W.
3. При расхождении проверки с утверждённым размером сохранён утверждённый размер; расхождение отмечено и не вызвало автоматического пересчёта макета.
4. Количество промежутков считается через ceil(N)−1; Web-формула не подставляется.
5. Gap привязан к rail/gap-horizontal/phone или tablet; screen padding относится к iOS.
6. Выбрана стандартная Rail Card, Custom или кастомная карточка; пропорция обложки соответствует концепту.
7. Скругления взяты из системы Rail Card, привязки сохранены, темы проверены.
8. Сохранены связи с мастерами, платформенными базами, стилями и переменными.
9. Проверены все карточки, скрытые слои, оба слота, лейблы, оверлеи, подписи, состояния и индивидуальные переопределения.
10. При включении скрытых элементов и изменении размеров нет случайных наложений и обрезки текста.
11. Проверены общий заголовок, нейминг, плоская структура мастеров и расположение запчастей.
12. Все расхождения, правила округления и неподтверждённые токены перечислены отдельно.
