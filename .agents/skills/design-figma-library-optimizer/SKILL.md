# Okko Figma Library Optimizer

Оптимизируй библиотеку так, чтобы дизайнер быстро находил нужный компонент, а изменения не ломали существующие инстансы и реализацию.

## Источники и границы

- Считай живую Figma основным источником структуры страниц, нод и component sets.
- Для fileKey, branchKey, nodeId, lifecycle и принадлежности библиотеке используй маршрут `design-figma-libraries` и его `references/libraries-map.md`.
- Перед Figma-вызовами загружай обязательные prerequisite skills текущего инструмента; перед `use_figma` обязателен `figma-use`.
- Аудит не даёт разрешения на запись. Изменяй Figma только по явному запросу пользователя.
- Не регистрируй и не синхронизируй локальную базу компонентов без отдельного явного запроса.

## Роль страницы

Перед оптимизацией определи тип страницы:

- platform guideline или демонстрация без публикуемых Assets;
- страница публичных компонентов;
- product components или templates;
- служебная, draft, WIP или deprecated-страница.

Не создавай Sections ради Assets: Sections влияют только на навигацию по холсту. Добавляй их, только если они заметно упрощают чтение большой страницы. Для небольшой страницы с одним-двумя семействами предпочитай плоскую структуру без лишней вложенности.

## Порядок и naming

- По умолчанию группируй страницы по сценарию использования компонентов, а не по алфавиту.
- Перед массовой перестановкой или перенумерацией покажи полную предлагаемую карту и получи согласование. Не утверждай временный порядок как окончательный.
- Нумеруй страницы или папки, влияющие на порядок Assets. Используй последовательный формат `01 · Name`, `02 · Name` и определяй номер по живой структуре файла — не угадывай его.
- Не добавляй номера в имена `COMPONENT` и `COMPONENT_SET`.
- Страницы-гайды без публикуемых Assets обычно не занимают номер в последовательности, если пользователь не установил другое правило.
- Для компонентов используй плоское имя `Group - Component`; не создавай глубокую иерархию через `/`, если она не была отдельно согласована.
- Lifecycle обозначай принятым цветным префиксом из `libraries-map.md`; не придумывай новый статус. Готовый реализованный компонент может иметь `🟢` или оставаться без статуса по решению владельца библиотеки.
- Добавляй в description назначение, ограничения, платформу, системные термины и короткий список поисковых тегов. Не используй скрытые служебные слои как замену description.

## Безопасная оптимизация

- Сначала зафиксируй IDs, родителей, абсолютные координаты, размеры, количество variants и публичные свойства затрагиваемых нод.
- При reparenting сохраняй абсолютные координаты и проверяй их после записи.
- Не меняй variants, component properties, размеры, auto layout, токены и поведение реализованного компонента без отдельного согласования.
- Не делай рискованный structural refactor только ради единообразия страницы. Naming, descriptions, статусы и навигацию исправляй отдельно от внутреннего устройства компонента.
- Product component, реализованный вне кодового пакета ДС, можно пометить ready, но явно укажи в description, что он не входит в кодовую дизайн-систему.
- В Lib-iOS системные элементы могут оставаться design-only референсами для компоновки макетов. Не выноси их в отдельную библиотеку без явного решения владельца; сохраняй разные клавиатуры для разных сценариев.

## Проверка результата

После записи проверь:

- порядок и названия страниц;
- поиск и читаемость имён в Assets;
- отсутствие случайных `/` и числовых префиксов у компонентов;
- lifecycle и descriptions;
- неизменность variants, размеров и поведения;
- отсутствие лишних Sections и сломанной вложенности;
- визуальный результат скриншотом.

В результате перечисли изменённые страницы и component sets, отдельно отметь сохранённые инварианты и решения, которые ещё требуют согласования.
