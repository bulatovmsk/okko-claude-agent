# Okko Layout Helper

Собирай решение из существующих компонентов и правил ДС. Результат может быть структурной спецификацией или изменением в Figma — в зависимости от запроса.

## Подготовка

1. Определи платформу, продуктовый контекст, главную задачу пользователя и доступные состояния экрана.
2. Если этих данных достаточно для разумной первой версии, не останавливайся ради подтверждения очевидного.
3. Начни с `references/generated/agent-index.json`: выбери компоненты lifecycle `ready` из нужной платформенной библиотеки. Детали найди в `references/components/`, токены — в `references/tokens/`, правила платформы — в `references/platforms/`.
4. Не подставляй воображаемый компонент. Отсутствующие части вынеси в отдельный список с допустимой заменой или вопросом к команде ДС.

## Проектирование

- Построй иерархию сверху вниз и укажи реальные имена компонентов и properties.
- Привяжи цвета и документированные размеры к существующим источникам.
- Покажи состояния loading, empty, error, disabled и focus только когда они релевантны сценарию.
- Для веб-кнопки выбирай состояние по фактическим вариантам [Button — Web](../design-ds-librarian/references/components/button-web.md): на Mobile нет `Hover`/`Focus`, а `Progress` доступен лишь для части текстовых `Rectangle`. Её `Breakpoint` соответствует роли `Device` у iOS Button, но значения и размеры бери из целевой библиотеки.
- Для TV задай логичный focus order и возврат фокуса.
- Для iOS и Android учитывай safe area, hit-area, системную навигацию и жесты.
- Если допустимы несколько паттернов, сравни их условия и дай рекомендуемый вариант.
- Для адаптации между iOS, Android и Web mobile/tablet используй только `confirmed` из `references/mappings/platform-mappings.json`; `candidate` покажи как неподтверждённый gap.

## Figma

### Адаптация составного компонента

- Разделяй источники правил: исходный UI Type, названный пользователем аналог и целевая библиотека. Уточни, какие характеристики берутся у аналога; сходство Featured и баннера само по себе не разрешает заменить пропорции, fade или состав действий.
- Перед заменой вложенного компонента проверь конкретный main component, платформенный вариант и доступные свойства. Публичные свойства, слоты, текст, иконки и видимость после swap могут отличаться. Существующую Meta переиспользуй целиком, не достраивай её поля независимыми слоями баннера.
- Читай фактические свойства Figma даже при наличии локальной карты соответствий. Новое сопоставление, проверенное в текущей задаче, можно применить в её рамках; это не основание молча публиковать его как общий confirmed mapping.
- Если текущая библиотека не предоставляет нужное поведение (например, Selected у кнопки избранного), визуально похожая кнопка не подтверждает эквивалентный контракт. Зафиксируй ограничение и не объявляй поведение реализованным.
- При изменении размеров сравни width/height с targetAspectRatio и проверь ограничения детей: fade, блок Meta с действиями, лейблы и управление звуком. Не масштабируй шрифты и отступы вместе с контейнером без соответствующего требования.
- Проверяй все затронутые сочетания: длинные действия, вертикальную и горизонтальную группы, оба состояния медиа. Локальный компактный размер кнопок может решить переполнение, но это отдельное решение адаптации, которое нужно отразить в документации, а не общее правило для платформы.

Если пользователь просит именно создать или обновить макет и доступна Figma-запись, работай в указанном файле. Перед каждым Figma-инструментом загружай обязательные prerequisite skills текущей среды. Сохраняй существующие компоненты, variables и auto-layout; не отсоединяй инстансы без необходимости.

Если Figma недоступна, выдай самодостаточную спецификацию, не утверждая, что макет создан.

После изменения текста или состава компонента проверяй экземпляры в фактическом контексте экрана: наличие property не гарантирует наличие связанного слоя, а прежняя высота контейнера может не вместить новый текст. Сверяй вложенные gap/padding и видимые границы после переключения нужных properties; подтверждай результат скриншотом. Для переноса изменений между платформенными master-компонентами используй маршрут `design-figma-libraries` → `references/component-parity.md`.

## Формат спецификации

Верни:

- цель и платформа;
- иерархию экрана;
- компоненты, properties и токены;
- сетку и ключевые отступы из источников;
- состояния и навигацию;
- отдельный список того, чего нет в текущей ДС.

Для созданного Figma-макета дополнительно укажи файл/фрейм и что требует ручной проверки.
