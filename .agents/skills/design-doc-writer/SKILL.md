# Okko Component Doc Writer

Готовь гайдлайн компонента по каркасу ДС и, когда доступна запись, собирай его в указанном Figma-файле.

## Источники

1. Всегда прочитай `references/STRUCTURE.md`.
2. Определи нужные секции по свойствам и назначению компонента.
3. Читай только шаблоны выбранных секций из `references/section-templates/`. В текущем комплекте детальные шаблоны есть не для всех секций; отсутствие шаблона не заменяй выдуманным эталоном.
4. Для Dropdown Web и миграции документации Context Menu читай [Dropdown · Desktop Web](references/dropdown-web.md). Прежнее решение Context Menu Web заменено модификацией Dropdown; [старый референс](references/context-menu-web.md) сохраняется как история оформления. Эти решения не распространяются автоматически на мобильные платформы.

## Исследование компонента

- Используй Figma-ссылку пользователя как основной источник структуры, variants, component properties, размеров и состояний.
- Перед любым Figma-вызовом загружай обязательный prerequisite skill текущей среды; перед `use_figma` обязателен Figma-use workflow.
- Если Figma недоступна, работай по предоставленным данным и ясно отметь границы достоверности.
- Не добавляй свойства и варианты, которых нет у компонента.

## Актуальность источников

- Фактический `COMPONENT_SET` и подтверждённое поведение реализации приоритетнее существующего текста гайда.
- Перед переиспользованием старого гайда сверяй его состояния, свойства, ограничения, примеры и lifecycle с текущим компонентом. Не распространяй устаревшую документацию на другие компоненты.
- Overview с полной матрицей вариантов — тестовый стенд, а не пользовательский гайд. Используй его для проверки покрытия, но не выводи из него правила применения и Do/Don't.
- `Button / Overview` можно использовать как эталон представления variants и regression board; расположенные рядом Button-гайды не считать актуальным каноническим источником без отдельной проверки.
- Если компонент и гайд противоречат друг другу, зафиксируй расхождение и меняй формулировку только на основании подтверждённого поведения.

## Разделение документации

По умолчанию оформляй документацию компонента двумя отдельными фреймами со взаимными ссылками:

- **Паспорт компонента** — техническая информация для разработки: API, свойства и события, фактические переменные Figma и стили с местами использования, зависимости и ограничения реализации. Предлагаемый API явно отделяй от подтверждённого API реализации.
- **Гайд по использованию** — общая документация для дизайнеров и разработки: назначение, сценарии, анатомия, сборка, варианты, размеры, состояния, поведение, позиционирование, Do/Don't, примеры и связанные компоненты.

Правила размеров и поведения оставляй в гайде; технический контракт и подробный перечень токенов — в паспорте, без дублирования. Краткие ссылки на токены в анатомии допустимы. При текстовой выдаче также разделяй эти два документа. Если пользователь уже вынес паспорт в отдельный фрейм, сохраняй это разделение и его названия.

Паспорт описывает только документируемый компонент: его API, публичные свойства, собственные токены и стили. Не включай подробные параметры внутренних запчастей и вложенных компонентов; оставляй ссылки на их документацию. Публичные свойства самого компонента, управляющие внутренними частями, сохраняй. Оформляй паспорт заголовками H2/H3, короткими списками и таблицами свойств и токенов вместо сплошных текстовых блоков.

## Состав гайдлайна

Для нового гайда используй порядок из `STRUCTURE.md`; при обновлении сохраняй пользовательскую перестановку секций.

- Обязательные секции включай всегда, кроме условных, которые не относятся к компоненту.
- Варианты, размеры, состояния, иконки и текст включай только при наличии соответствующего свойства или поведения.
- Компонент-специфичные секции добавляй, когда без них нельзя объяснить важное правило.
- Do/Don't основывай на подтверждённых сценариях; спорные примеры помечай для проверки дизайнером.
- Визуальная анатомия дополняет текстовую: сохраняй описание и показывай инстанс компонента с фиолетовыми нумерованными выносками и легендой. Переиспользуй шаблон Pointer; проверяй направление выносок и соответствие номеров частям компонента.
- Проверяй полноту анатомии по слоям и публичным переключателям, включая скрытые опциональные части. Если часть видна только при переполнении или другом условии, показывай подходящий демонстрационный инстанс и подписывай условие. Не ограничивай число выносок ценой пропуска значимой части.
- Правила размеров, сборки, состояний, поведения и Do/Don't сопровождай наглядными примерами. Используй связанные инстансы для фактического вида и явно подписанные схемы для условных примеров; не изобретай отсутствующие состояния. Сохраняй пользовательские иллюстрации и их порядок.
- Ссылки на компоненты и между гайдом и паспортом делай кликабельными и выделяй фиолетовым.
- В связанных компонентах по возможности размещай настоящие инстансы рядом с описанием и ссылкой. При обновлении применения сверяй подписи с актуальными пользовательскими скриншотами.

## Создание в Figma

Если пользователь попросил создать или обновить гайдлайн и дал целевой файл:

1. Сохрани variables, styles, компоненты и auto-layout существующей библиотеки.
2. Переиспользуй доступные шаблонные секции и существующие инстансы вместо ручной имитации.
3. Заполни тексты, анатомию, properties, состояния и контекстные примеры данными целевого компонента.
4. Не отсоединяй инстансы и не меняй исходный компонент без необходимости.
5. После записи проверь структуру и визуальный результат доступными средствами: отсутствие обрезки и пересечений, читаемость подписей, соответствие номеров легенде, точность концов выносок, связи инстансов и назначения ссылок. Подтверди сохранность пользовательских правок и исходных компонентов.

Если записи нет, выдай полный план гайдлайна и черновики текстов, не утверждая, что Figma-фрейм создан.

## Результат

Сообщи:

- где находится созданный или обновлённый фрейм;
- какие секции включены и почему;
- что заполнено из данных компонента;
- какие формулировки и Do/Don't требуют ручной проверки;
- какие данные отсутствовали.
