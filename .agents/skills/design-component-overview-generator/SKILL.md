# Okko Component Overview Generator

Создавай обзорный фрейм, по которому дизайнер и разработчик могут одновременно проверить покрытие variants и визуальную консистентность компонента.

Эталон принципа — `Button / Overview`, node `34198:23721` в рабочем Lib-iOS. Используй его как пример тестовой матрицы, но не считай расположенную рядом документацию актуальным эталоном.

Для Chips Web используй [контекст компонента](../design-figma-libraries/references/chips-web.md): отдельные Overview Small/Default и допустимые пропуски Mobile.

Для Select Web используй [контекст Select](../design-figma-libraries/references/select-web.md): существующие Overview Default/Small/Large, 84 варианта в снимке и шесть отсутствующих Mobile Focus. Mobile Hover у Select есть — не переноси пропуски Chips.

Для Button и Button Toggle Web читай [контекст кнопок](../design-figma-libraries/references/buttons-web.md): актуальные гайды и паспорта, ограничения вариантов, Selected и пересобранный Overview Button. Не переносить свойства iOS или обычного Button в Toggle автоматически.

## Источник комбинаций

- Читай variants и component properties непосредственно из целевого `COMPONENT_SET` в живой Figma.
- Используй только существующие валидные варианты. Не генерируй полный декартов набор значений, если таких вариантов нет в component set.
- До построения составь список уникальных комбинаций, дублей и пропусков. Пропуск может быть допустимым ограничением компонента — не создавай недостающий variant автоматически.
- Если на странице несколько публичных component sets, создавай отдельный Overview для каждого семейства.

## Компоновка матрицы

Выбирай оси по смыслу свойств:

- `State` — основные колонки;
- `Device` — подколонки внутри состояния;
- `Style`, `Type` или основная визуальная вариация — крупные группы строк;
- `Size` — строки внутри группы;
- `Shape`, `Text`, `Selected` и другие boolean/structural свойства — отдельные подгруппы или отдельные Overview, если одна матрица становится нечитаемой.

Если у компонента нет `State` или `Device`, выбери две оси, которые лучше всего помогают сравнению. При высокой сложности разделяй матрицу по одному из свойств вместо создания одного огромного фрейма.

Неподдерживаемые сочетания оставляй пустыми. Не подменяй отсутствие варианта похожим инстансом.

## Создание в Figma

- Перед записью загрузи обязательный `figma-use` skill и соблюдай его правила.
- Создавай реальные связанные instances из соответствующих variant-компонентов; не detach.
- Не меняй исходный component set, его variants, свойства, размеры, токены или порядок вариантов.
- Используй существующие стили, variables и оформление библиотеки. Если в файле есть подходящая шапка Overview, переиспользуй её вместо имитации.
- Предпочитай вложенный auto layout для заголовков, групп, строк и ячеек. Фиксированный размер ячейки допустим для ровного визуального сравнения.
- Именуй результат `Overview · <Component>` или по действующей конвенции страницы. В комплекте «компонент — гайд — паспорт» размещай Overview в левой области общей секции без имени по [эталону оформления](../design-doc-writer/references/component-presentation.md); не создавай для него дополнительную секцию. Для самостоятельного Overview секция не нужна, если фрейм и без неё читается.
- Не перезаписывай вручную собранный Overview без явного разрешения. При сомнении создай новый фрейм рядом и обозначь его как generated draft.

## Проверка покрытия

После генерации проверь:

- каждый валидный variant представлен нужное число раз;
- у каждого instance есть связь с main component;
- подписи совпадают с фактическими property values;
- пустые ячейки соответствуют отсутствующим комбинациям;
- нет detached-копий, обрезанного текста и наложений;
- исходный component set не изменился;
- фрейм визуально читается на скриншоте.

Верни количество variants, instances, найденных дублей и пропусков, а также ID созданного Overview.

## Отделение от документации

Overview — это тестовый стенд и инвентаризация вариантов. Не выводи из него правила применения, Do/Don't или продуктовые сценарии. Для пользовательского гайда используй `design-doc-writer` и отдельно проверяй актуальность существующей документации.
