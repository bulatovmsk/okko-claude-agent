# Okko DS — Doc Writer

Skill пишет документацию компонента ДС Окко в Figma. Не свободная форма — единый шаблон, согласованный с эталонами (Button, BottomSheet, TabGroup).

## Когда срабатывать

- «Напиши гайдлайн для компонента X»
- «Оформи документацию для Y»
- «Сделай гайд для нового компонента в библиотеке»
- «Задокументируй компонент в Figma»

НЕ срабатывать на запросы про:
- README-файлы кода (это другая задача, обычный код-помощник)
- Документацию проекта/команды (это не гайдлайн компонента)
- Аудит существующего гайдлайна (передать `okko-ds-auditor`)

## Что я знаю

- Полный каркас гайдлайна — в `references/STRUCTURE.md`
- Шаблоны каждой секции — в `references/section-templates/`
- Эталоны в библиотеке Окко (для примеров):
  - Button — `node-id=31214-29705`
  - BottomSheet — `node-id=28934-239837`
  - TabGroup — `node-id=24233-7754`
  - File: `Lib-iOS` (fileKey `rMcDm5qGp4CXkXXddEbcMh`)

## Алгоритм работы

1. **Уточни вводные:**
   - Какой компонент документируем? (имя + ссылка на компонент в Figma)
   - Это новый гайдлайн или обновление существующего?
   - Платформа iOS, или нужно расширить под Android/Web/TV?

2. **Изучи компонент через Figma MCP:**
   - `get_design_context` → variants, sizes, properties
   - `get_metadata` → структура слоёв (имена частей для анатомии)
   - `search_design_system` → найти, где компонент уже используется (для примеров)

3. **Определи состав секций:**
   - Обязательные: 1 (Шапка), 2 (Когда), 3 (Когда не), 4 (Анатомия), 5 (Настройки), 12 (Do/Don't), 14 (Применение)
   - Рекомендованные — включай, если в компоненте есть соответствующие свойства:
     - Секция 6 (Варианты) — если у компонента есть Type/Variant property
     - Секция 7 (Размеры) — если есть Size property
     - Секция 8 (Состояния) — если компонент интерактивный
     - Секция 9 (Иконка) — если есть Icon slot
     - Секция 10 (Отступы) — почти всегда
     - Секция 11 (Текст) — если есть текстовый слот
   - Компонент-специфичные (13) — спроси у пользователя, нужны ли уникальные секции

4. **Подтверди план с пользователем:**
   - Покажи список секций, которые будут в гайдлайне
   - Подсветь, какие данные я возьму автоматически, а какие нужны от него
   - Дождись «ок»

5. **Сгенерируй гайдлайн в Figma:**
   - Создай новый фрейм 2776px ширины (или попроси создать вручную, если нет доступа на запись)
   - Для каждой секции — скопируй соответствующий шаблонный фрейм из библиотеки и заполни:
     - Title → название секции
     - Иллюстрации → инстансы компонента / реальные экраны
     - Pointer-аннотации → подписи с токенами
     - Тексты → драфты на основе данных компонента
   - Используй `use_figma` MCP для создания фрейма и копирования секций
   - **MANDATORY:** перед `use_figma` загружай `/figma-use` skill

6. **Сообщи о готовности и о ручных доработках:**
   - Что заполнено автоматически
   - Что требует ручной проверки дизайнером (особенно — Do/Don't примеры, формулировки)
   - Где разместил итоговый фрейм

## Где данные

```
references/
├── STRUCTURE.md                # каркас гайдлайна — главное
└── section-templates/          # по одному файлу на секцию
    ├── 01-header.md
    ├── 02-when-to-use.md
    ├── 04-anatomy.md
    ├── 12-do-dont.md
    └── ...
```

Синхронизируется из `design-system/guidelines/` корня репозитория через `scripts/pack-skills.sh`.

## Формат вывода

В чат — структурированный план + ссылка на созданный/обновлённый фрейм в Figma:

```markdown
## Готов гайдлайн: <название компонента>

**Фрейм в Figma:** [ссылка]

### Состав секций (X из Y возможных)
- ✅ 1. Шапка
- ✅ 2. Когда использовать
- ...
- ⏭️ 11. Текст — пропустил, у компонента нет текстового слота

### Что заполнено автоматически
- Анатомия — извлечена из структуры компонента
- Состояния — из таблицы variants
- Настройки — из свойств

### Что требует твоей проверки
1. **Do/Don't примеры** — я написал драфты, но проверь, что антипаттерны реалистичны
2. **Иллюстрации в контексте** — подобрал 3 экрана, но возможно есть лучше
3. **Подзаголовок в шапке** — мой драфт: «...». Поправь, если что
```

## Ограничения

- **Не выдумываю свойства** компонента. Если в Figma нет Variant=Ghost — секцию про Ghost не делаю.
- **Не заменяю дизайнера в спорных решениях** — Do/Don't примеры и формулировки помечаю как «требует проверки».
- **Не нарушаю порядок секций** из STRUCTURE.md.
- **Работаю только с iOS-библиотекой** по умолчанию. Для других платформ — спрашиваю явно.
