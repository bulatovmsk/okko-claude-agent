# Skill: сборка UI Type Rail Okko

Создай Rail по концепту дизайнера любой детализации: вайрфрейм, текст, изображение или подробный макет. Общий запрос охватывает все 14 размеров iOS/Android/Web, включая Desktop. Явное ограничение пользователя имеет приоритет.

Эта инструкция самостоятельна для Figma Agent. Используй доступные ему средства чтения, импорта связанных компонентов и редактирования Figma. Имена инструментов Codex и локальные пути не требуются. При отсутствии нужной возможности сообщи точное ограничение, сохранив уже сделанную независимую работу.

Разбери концепт, найди реальные компоненты и зависимости, собери варианты и проверь результат по следующим правилам. Новых переменных и токенов не создавай. Сначала проверь живую библиотеку: приведённые ID и измерения являются датированным снимком.

## Разбор концепта

# От концепта к UI Type

Концепт может быть вайрфреймом из прямоугольников, подробным дизайном, изображением или текстовым описанием. Низкая детализация сама по себе не мешает сборке. Текущий навык поддерживает Rail; Grid и другие будущие UI Type требуют собственных правил.

## Роль инструмента и дизайнера

Инструмент помогает дизайнеру выполнить основную работу: собирает полноценную связанную компонентную основу на всех запрошенных платформах, применяет платформенные правила и предлагает исходные настройки. Дизайнер оценивает результат, донастраивает композицию и визуальные параметры и принимает окончательное решение.

Рекомендательные шкалы, в том числе подбор радиуса по минимальной стороне, помогают сделать первоначальный выбор. Они не являются абсолютным критерием правильности. Явный выбор дизайнера имеет приоритет над рекомендацией; сохраняй его при последующих пересборках и не возвращай автоматически к шкале.

Свобода визуальной донастройки сохраняет компонентные зависимости и использование существующих токенов: радиус по-прежнему выбирается из системы Rail Card. Отличие от рекомендованной ступени само по себе не является ошибкой.

Не используй последующее ревью дизайнера как основание оставить неполную сборку: агент завершает согласованное покрытие платформ, проверяет структуру и зависимости и передаёт пригодную для редактирования основу. Найденные при проверке ошибки показываются дизайнеру без автоматических исправлений; полное покрытие устройств сохраняется. Успешная сборка и техническая проверка не означают дизайнерского утверждения.

## Вход и решения

Прочитай весь предоставленный концепт, а при наличии исходного Rail — все его карточки и скрытые возможности. Выдели:

- смысл и повторяемую единицу: карточка или колонка из нескольких карточек;
- обязательный контент, порядок, ряды, подписи, состояния и действия;
- пропорции обложки, характер шапки и возможные исключения платформ;
- целевую библиотеку и запрошенный охват.

По умолчанию общий запрос означает iOS, Android Mobile и Web с Desktop. Если концепт дан только на одном размере, не считай этот размер ограничением платформенного охвата.

Для каждого решения различай «задано дизайнером», «взято из проверенного библиотечного образца» и «допущение». Сохраняй смысл, порядок контента и действия. Не копируй случайные пиксельные размеры вайрфрейма в платформенные компоненты.

Визуальные детали, не указанные дизайнером, бери из проверенных существующих компонентов: типографику, радиусы, встроенные состояния и отступы. Не добавляй действия, контентные поля или новые состояния только ради полноты.

Для плотности N, span, фиксированных iOS-размеров и платформенных различий ищи подходящее проверенное семейство Rail и указывай, что именно наследуется. Для нового типа допускается предложить геометрию по формуле как черновик. Не называй новые размеры утверждёнными, пока дизайнер их не проверил. Правило сохранения утверждённых iOS-размеров относится к существующим значениям, а не запрещает проектировать новый тип.

Вопрос необходим, если неизвестны смысл, обязательный состав, действие или выбор, который существенно меняет композицию. Продолжай независимую понятную часть. Не выдавай разные существенные трактовки за один согласованный концепт.

## Компонентный план

До записи составь компактное соответствие «элемент концепта → мастер → платформа → слот/свойство → источник размера».

Rail Card и Rail Heading — из UI Type. Базовые компоненты — из библиотек соответствующих платформ или подтверждённых общих библиотек. Доступный опубликованный компонент подгружается/импортируется как связанный instance. Если компонент недоступен для импорта, сообщи конкретную зависимость; не рисуй копию и не detach ради обхода.

Уникальная запчасть создаётся только при отсутствии совместимой существующей. Её мастер находится рядом с Rail; внутри сохраняются платформенные базовые экземпляры. Перенос из другой платформы требует проверки типографики, свойств, токенов и состояний.

## Полная сборка

| Набор | Геометрические варианты |
|---|---|
| iOS | iPhone 15, iPhone 17 Pro Max, iPad Mini 6, iPad 10, iPad Pro 13 |
| Android | Phone 360, Tablet P 640, Tablet L 1024 |
| Web | breakpoint 320, 375, 768, 1024, 1440, 1920 |

Всего 14 вариантов в трёх основных component sets, стоящих в ряд. Существующие согласованные свойства состояний сохраняются; их комбинации могут увеличивать число вариантов. У каждой платформы своя модель расчёта. Геометрические варианты не заменяются общей карточкой Phone/Tablet.

Используй auto layout, настоящие слоты и сохранённые библиотечные связи. Не создавай всю секцию нарисованными копиями. Для стандартной структуры выбирай фиксированную пропорцию или Custom по порогу 15% из общих правил: отклонение до 15% включительно от подходящей фиксированной пропорции означает её использование; больше 15% от всех подходящих — Custom по умолчанию. Полноценную кастомную структуру реализуй отдельным локальным мастером.

## Проверка и передача

Следуй проверке на устройствах: покажи связанные экземпляры на всех обязательных экранах с включёнными локальными сетками. Ошибки сообщай дизайнеру без автоматического исправления.

Сопоставь результат с концептом по смыслу и составу. Затем проверь покрытие 5/3/6, происхождение экземпляров, внутренние слоты, скрытый контент, размеры обложки отдельно от подписи, переменные и темы, нейминг и расположение.

На всех обложках новой сборки должна быть дефолтная картинка-плейсхолдер библиотеки по общим правилам, даже если концепт содержит серые прямоугольники или контентные изображения.

Дай ссылки на три набора, таблицу фактических размеров и источников расчёта, результат проверки и существенные допущения. Отличай структурную проверку от визуальной и от дизайнерского утверждения.

## Проверка навыка на новом концепте

Используй новый предоставленный дизайнером концепт. Запиши исходные требования до сборки, затем сравни результат с ними и правилами без изменения критериев задним числом. Проверяй итоговые узлы, а не только успешное выполнение команд.

Для первого теста создай отдельную тестовую страницу в рабочей библиотеке и понятные имена. Исходные Rail и платформенные библиотеки не изменяй. При запросе на обновление навыка исправь подтверждённые проблемы его инструкций и повтори затронутые проверки. Ошибки Figma-сборки сообщай дизайнеру без автоматического изменения макета. Тест через Codex не подтверждает выполнение тем же навыком внутри Figma Agent: такой запуск отмечается отдельно.

До получения концепта тестовая сборка ожидает входные данные. Не придумывай за пользователя тестовый тип и не объявляй тест выполненным.


## Общие правила

# Общие правила Rail

Приняты в работе с библиотекой UI Type 11–13 ноября 2026; сохранены 16 ноября. Последние явные решения пользователя имеют приоритет над старыми источниками. Снимки геометрии проверяй в живой Figma перед изменением.

## Архитектура и источники

Агент выполняет основную сборку и проверку; дизайнер донастраивает результат и принимает окончательные визуальные решения. Рекомендательные шкалы помогают первоначальному выбору и не отменяют явную настройку дизайнера. Сохраняй такие настройки при пересборке, используя существующие компоненты и токены.

Rail — композиция из шапки, карусели и карточек, иногда фона, спонсорских или других блоков. Rail Card — повторяемая карточка, не весь UI Type.

Рабочая библиотека: [UI Type Web & Mobile](https://www.figma.com/design/TGfdPRzrhCA6CbiHsRjBSD?node-id=0-1).

- Rail Card iOS, Android и Web находятся локально на странице Rail Shared этой библиотеки. Используй экземпляр соответствующей платформы.
- Rail Heading — один общий компонент в UI Type. Phone и Tablet общие для платформ. Desktop уже добавлен: увеличены типографика/изображения, правая стрелка шапки скрыта.
- Label, Rich Label, кнопки и другие базовые элементы остаются экземплярами Lib-iOS, Lib-Android-Mobile, Lib-Web или подтверждённой общей базовой библиотеки.
- Уникальные детали конкретного типа хранятся локально рядом с Rail. Сначала ищи подходящие существующие подписи, оверлеи, прогресс и другие запчасти. Разница только в ширине не требует нового мастера.
- Поддерживаемое состояние Skeleton берётся из Rail Card; отдельный дубликат скелетона не создаётся.
- Исходные Rail в платформенных библиотеках используются для чтения. Их перенос не разрешает правку или удаление исходников. Ранее отдельно разрешённое удаление старых мастеров карточки не распространяется на исходные Rail.

## Три способа собрать карточку

| Способ | Применение |
|---|---|
| Rail Card со стандартным Shape | Нужны стандартные структура и пропорции |
| Rail Card, Shape=Custom | Подходит структура, нужны свободные пропорции |
| Полностью кастомная карточка | Нужны другая структура или поведение |

Стандартные пропорции обложек: Horizontal 16:9, Vertical 2:3, Square и Circle 1:1. Высота подписи и её интервалы считаются отдельно. У Custom общая высота экземпляра включает подпись, обложка занимает остаток. Нельзя считать общую высоту карточки высотой обложки.

Пользователь разрешил кастомные пропорции и собственные карточки. Прежнее временное правило «не переносить несовместимые с Rail Card пропорции» отменено. Rail Ticket удалён пользователем; не восстанавливай его из старых отчётов.

### Выбор фиксированной пропорции или Custom: порог 15%

Для нового концепта перед выбором Shape=Custom сравни пропорцию обложки с доступными фиксированными пропорциями подходящей Rail Card:

ratioConcept = ширина обложки концепта / высота обложки концепта
ratioFixed = ширина / высота фиксированной пропорции
differencePercent = abs(ratioConcept - ratioFixed) / ratioFixed × 100

Выбирай фиксированную пропорцию с минимальным differencePercent среди совместимых по структуре и форме вариантов. Если отклонение не превышает 15% (включая ровно 15%), используй её. Если от всех подходящих фиксированных пропорций отклонение больше 15%, по умолчанию используй Shape=Custom с пропорцией концепта; отдельное подтверждение только для такого выбора не требуется.

При фиксированной пропорции пересчитай высоту обложки по выбранной ширине и ratioFixed. При Custom — по ratioConcept. Подпись, шапка и отступы в измерение пропорции не входят. Не округляй отклонение до сравнения с порогом.

Например, относительно 16:9 пропорция 1,6 отклоняется на 10% — используется 16:9. Пропорция 2,1 отклоняется примерно на 18,125% от 16:9 — используется Custom, если нет другой подходящей фиксированной пропорции в пределах 15%.

Равная пропорция Square/Circle не определяет форму: сохраняй заданную дизайнером геометрию. Правило выбора пропорции не заменяет проверку структуры; при иной структуре нужна полноценная кастомная карточка. Оно не разрешает автоматически менять уже утверждённые размеры существующих Rail.

## Дефолтная картинка обложки при сборке по концепту

На каждой обложке нового UI Type по концепту всегда используй существующую дефолтную картинку-плейсхолдер библиотеки. Правило действует для всех карточек и вариантов iOS, Android и Web, включая стандартные формы, Custom и полностью кастомные карточки. Сохраняй дефолтную картинку подходящей Rail Card; для кастомной структуры переиспользуй тот же библиотечный плейсхолдер.

Не заменяй его серой заливкой из вайрфрейма, пустой обложкой или контентной картинкой из концепта. Тексты, оверлеи и исходную видимость элементов концепта переноси независимо от картинки обложки. Сохраняй технический слой Cover, пропорции, скругление, clipping и компонентные связи. Встроенный Skeleton остаётся отдельным состоянием и не заменяет плейсхолдер обычного состояния.

При проверке новой сборки проверь фактическое наличие дефолтной картинки на каждой обложке, а не только имя слоя Cover. Если дефолтный плейсхолдер не найден или недоступен, сообщи об ограничении; не генерируй и не придумывай замену. Это правило сборки по концепту не разрешает автоматически менять изображения в уже существующих UI Type при аудите.

## Токены

Радиус новых карточек выбирается по минимальной стороне скругляемого Cover после выбора пропорции: S=min(W,H). Ступени и реальные ограничения текущей библиотеки описаны в radius.md. Подбирается существующий токен Rail Card с сохранением темы; предлагаемая beta-шкала не меняет автоматически утверждённые радиусы и не заменяет круглую геометрию Circle.

- Между карточками: локальные rail/gap-horizontal/phone=6, tablet=8, desktop=10. На Web 1440 используется tablet=8 при Device=Desktop.
- Радиусы карточки и обложки выбираются только из системы Rail Card через rail/card/radius/*. Привязки поддерживают смену темы. Не копируй текущее число и не подставляй сторонний radius-токен. Сохраняй круглую геометрию Circle и собственные токены вложенных кнопок/лейблов.
- Внутренние padding/gap отличаются от gap карусели. Пользователь требует компонентное семейство Rail Card Padding Gap, но точный путь ещё не подтверждён. В проверенных Labels / padding были числовые 6 и 2 без привязки. До подтверждения сохраняй мастер и явно отмечай незавершённую токенизацию; не выдумывай путь и не заменяй его rail/gap-horizontal/*.
- Screen padding выбирается по платформе. Не вычитай его повторно, если родитель уже ограничил полезную область.
- Запрещено создавать новые дизайн-переменные, aliases, коллекции и токены. Разрешён импорт уже существующих переменных. При отсутствии нужной сообщи об ограничении.
- Token Studio repo — источник для чтения: bulatovmsk/token-studio-repo, main. При новых выводах о токенах проверяй актуальный commit; сохранённые значения имеют дату проверки.

## Структура

Страница Rail <тип>; компоненты Rail <тип> iOS, Rail <тип> Android, Rail <тип> Web. Все запчасти, включая общие, публикуются в группе `x / `: `x / Rail <тип> <роль> [платформа] [размер]`. Для наполнения слотов: `x / Rail <тип> Slot <роль> [платформа] [размер]`. Не скрывай запчасти через `_`. Основные Rail, базовые Rail Card и Rail Heading остаются без `x / `. Не добавляй общий префикс UI Type и длинную иерархию через дроби. Для будущего Grid будет свой префикс.

Мастера лежат прямо на странице без SECTION и лишних контейнеров, платформы слева направо iOS → Android → Web. Запчасти рядом; общие запчасти в одном экземпляре. Проверку размещай в отдельных платформенных секциях с экранными фреймами по device-review.md. Запрет секций-обёрток относится к мастерам.

На Rail Shared собраны базовые Rail Card и Heading, Rail Example, общие запчасти и примеры сеток. Rail Example — пример композиции; его экземпляр можно detach, сохранив связи вложенных базовых компонентов. Это разрешение не относится к Rail Card, Heading и другим базам.

Внутри Rail сохраняются полезные Carousel, Row, Column и другие функциональные контейнеры. Не добавляй Base Rail и одноэлементные обёртки без роли. Техническое имя слоя Cover сохраняется для подстановки изображений.

## Перенос и проверка

Проверяй все карточки, скрытые потомки и индивидуальные overrides, включая элементы, которые визуально не видны. Встроенные возможности Rail Card не дублируй отдельными деталями. Сохраняй исходное состояние видимости. Сначала переносится действующая часть, WIP исключена.

Обложка, подпись, шапка и суммарная высота Rail измеряются раздельно. У двухрядных типов различай карточку, колонку и два ряда. N в формулах — плотность расчётной области, а не число экземпляров, создаваемых в карусели.

Шапка растягивается по доступной ширине; скрытая шапка не оставляет лишний gap. Стрелка шапки и навигация карусели — разные элементы. У Carousel `clipsContent=false`; переполнение ограничивает внешний экранный фрейм проверки. Clipping обложки сохраняется независимо.

Проверяй реальные связи с мастерами, стили и переменные, а не совпадение названий. Включай скрытые возможности на собственных временных примерах и проверяй слоты, ресайз, обрезку и текст. Удаляй только свои временные узлы. Не объявляй визуальную проверку полной инвентаризацией скрытого контента.

## Правила структуры и проверки на устройствах

19 страниц, 205 вариантов платформенных наборов, 2118 экземпляров карточек с дочерним Cover FRAME (222 группы одинаковой геометрии/радиуса внутри вариантов). ## Применение через Rail Card

1. Выбрать стандартную пропорцию или Custom по правилу 15%, затем рассчитать фактические W/H обложки.
2. Найти S и токен по таблице. Выбор основан на размере, а не только на Phone/Tablet/Desktop или Shape.
3. Сохранить instance Rail Card нужной платформы; назначить существующую переменную выбранного уровня всем соответствующим углам скругляемого Cover. Не detach и не заменять переменную числом.
4. Сохранять базовые радиусы кнопок/лейблов внутри. Circle остаётся кругом. Правило применимо и к Shape=Custom.
5. Проверить реальные привязки и режимы Main/Meta, clipping и размер скругляемой области.

В проверенном Rail Card iOS отдельного component property Radius нет: доступны Shape и Device и свойства содержимого. Поэтому инструкция не должна обещать автоматическое переключение радиуса при resize или вызывать несуществующий Radius prop. Подбор делает агент при сборке; переменная задаётся на Cover внутри связанного экземпляра, если операция поддержана. Если переопределение недоступно, это конкретное ограничение, а не повод раздетачить карточку или изменить общий мастер для всех экземпляров.

## iOS

# Принципы сборки Rail iOS

Рабочая редакция от 13 ноября 2026 года. Документ основан на решениях из чата, текущей библиотеке UI Type и проверенном Technical(iOS) JSON. Правила сборки отделены от исторических размеров и известных расхождений.

Основное правило iOS: сохраняются утверждённые фиксированные размеры карточек для каждого устройства. Technical JSON используется для проверки и объяснения размеров. Расхождение с формулой или фактической шириной экранного макета само по себе не является основанием для пересчёта.

## 1. Состав Rail и исходный концепт

Rail — готовая композиция UI Type: общий заголовок, карусель и карточки. Фон, изображения, спонсорские и другие блоки подключаются по концепту.

До сборки определяются повторяемая единица, число рядов, содержание карточек, пропорции обложек, подписи и состояния. Повторяемой единицей может быть отдельная карточка или колонка из нескольких карточек.

При воспроизведении существующего типа проверяются все исходные карточки, включая скрытые слои и индивидуальные переопределения. Одного названия типа недостаточно для выбора геометрии и состава.

## 2. Источники компонентов

- Карточка — локальный Rail Card iOS из библиотеки UI Type.
- Заголовок — общий Rail Heading из этой же библиотеки.
- Label, Rich Label, кнопки и другие базовые компоненты — из Lib-iOS или подтверждённой общей базовой библиотеки.
- Уникальные запчасти создаются в библиотеке UI Type рядом с соответствующим Rail.
- Совместимые подписи, оверлеи и другие запчасти переиспользуются между типами и платформами. Разница только в ширине не требует нового мастера.
- При переиспользовании проверяются состав, свойства, типографика, токены, состояния и базовые зависимости.

Экземпляры сохраняют связи с мастерами. Базовые компоненты не заменяются нарисованными копиями. Правки Lib-iOS не входят в обычную сборку Rail в библиотеке UI Type.

|---|---|---|---|---:|---:|
| Device=iPhone 15 | 393 × 852 | Portrait | Phone | 15 | 363 |
| Device=iPhone 17 Pro Max | 440 × 956 | Portrait | Phone | 15 | 410 |
| Device=iPad Mini 6 | 1133 × 744 | Landscape | Tablet | 35 | 1063 |
| Device=iPad 10 | 1180 × 820 | Landscape | Tablet | 35 | 1110 |

Для iOS собираются пять фиксированных вариантов конкретных устройств. Один общий Phone и один общий Tablet не заменяют эти макеты. Внутренняя Rail Card и совместимые запчасти могут иметь только Phone/Tablet и получать нужный размер в экземпляре.

В библиотеке есть дополнительные шаблоны iPhone 13 mini и портретных iPad. Они не расширяют обязательный набор автоматически. Пометка Optional у экранного шаблона iPad Mini не исключает его из подтверждённого набора Rail.

## 4. Платформенные отступы и интервал

| Группа | Левый screen padding L, px | Правый расчётный R из Technical(iOS), px | Gap G, px | Токен интервала |
|---|---:|---:|---:|---|
| iPhone | 15 | 30 | 6 | rail/gap-horizontal/phone |
| iPad | 35 | 50 | 8 | rail/gap-horizontal/tablet |

Screen padding берётся из screen-padding/ios/iphone и screen-padding/ios/ipad.

R — полный правый расчётный отступ от края расчётной области. Он уже включает свою величину целиком: screen padding повторно к нему не прибавляется.

R используется в формуле размера карточки. Он не назначается автоматически как paddingRight карусели, не считается safe area и не вычитается повторно из уже рассчитанной ширины.

Фактический gap между карточками привязывается к локальным переменным rail/gap-horizontal/* из библиотеки UI Type. В формуле используется значение того же токена.

## 5. Формула ширины карточки iOS

Формула применяется как проверочный расчёт. Утверждённый фиксированный размер карточки имеет приоритет перед полученным результатом. Для нового типа формула помогает подготовить размеры к утверждению; она не отменяет отдельную фиксацию итоговой геометрии.

Ширина карточки = (расчётная ширина − левый screen padding − правый расчётный отступ − (количество промежутков × gap)) / ожидаемое количество карточек.

Количество промежутков = ожидаемое количество карточек, округлённое вверх, минус 1; минимум 0.

Обозначения для агента:

A = S − L − R
K = max(0, ceil(N) − 1)
W = (A − K × G) / N

Где:
- S — подтверждённая входная ширина для расчёта;
- A — расчётная область;
- L — левый screen padding;
- R — правый расчётный отступ;
- N — ожидаемое количество карточек или колонок в расчётной области;
- K — количество промежутков;
- G — интервал между карточками;
- W — ширина повторяемой карточки или колонки.

N задаётся для конкретного типа и устройства и может быть дробным. Например:
- N=1,5 → K=1;
- N=2,5 → K=2;
- N=3 → K=2.

Это iOS-правило. Web-формула с непрерывным N−1 сюда автоматически не переносится. Android использует свою сеточную модель.

N не означает количество экземпляров, которое нужно создать в карусели. Для двухрядного Rail горизонтальное N относится к колонкам; высота и вертикальные интервалы считаются отдельно.

N должно быть больше 0, расчётная область и полученная ширина — положительными. Промежуточные вычисления и дробное N не округляются произвольно.

## 6. Входная ширина S и действующие фиксированные размеры

Нужно различать:
1. фактическую ширину экранного макета;
2. полезную ширину Rail B;
3. входную ширину S выбранного расчёта;
4. полученную или утверждённую ширину карточки W.

В историческом Technical JSON S может отличаться от актуального экранного шаблона. Пользователь уточнил причину для среднего iPhone: во время редизайна Rail расчёт выполнялся по ширине 390 px; текущий экранный макет имеет ширину 393 px. Поэтому карточка Main 226 px соответствует исходной базе 390 и сохраняется как утверждённый фиксированный размер. Это объяснённое различие расчётной базы и экранного макета, а не основание автоматически исправлять карточку.

Историческую базу нельзя выдавать за фактическую ширину нового экрана. Совпадение имени устройства также не доказывает, что все входные данные уже обновлены.

Текущий Rail Main iOS имеет следующие размеры:

| Устройство | Фактическая ширина экранного макета, px | Текущая ширина карточки W, px | База S исторического Technical JSON, которая воспроизводит W | N Main в этом наборе |
|---|---:|---:|---:|---:|
| iPhone 15 | 393 | 226 | 390 — iPhone Regular | 1,5 |
| iPhone 17 Pro Max | 440 | 259,333… | 440 — iPhone Wide | 1,5 |
| iPad Mini 6 | 1133 | 214,333… | 744 — iPad Compact | 3 |
| iPad 10 | 1180 | 222,333… | 768 — iPad Regular | 3 |
| iPad Pro 13 | 1376 | 249,8 | 1366 — iPad Wide | 5 |

Связь с исторической базой здесь подтверждается совпадением вычисленных размеров. Таблица описывает текущие макеты и не устанавливает универсальную новую привязку устройств к Technical-наборам.

Исторический пример iPhone Regular:
W = (390 − 15 − 30 − 1 × 6) / 1,5 = 226 px.

Если для нового расчёта явно использовать фактическую ширину iPhone 15:
W = (393 − 15 − 30 − 1 × 6) / 1,5 = 228 px.

Это два разных набора входных данных. Нельзя назвать одновременно 226 и 228 одним и тем же результатом для одинакового S.

Подтверждённое решение: сохранять утверждённые фиксированные размеры карточек, JSON использовать для проверки. Для iPhone 15 в текущем Main сохраняется 226 px; проверочный результат 228 px не заменяет этот размер автоматически. То же правило действует для остальных устройств и типов.

Для нового типа фиксированные размеры определяются концептом и утверждаются по каждому устройству. Для пересборки существующего типа сохраняются его утверждённые значения. Изменение размеров является отдельной явно поставленной задачей, а найденные расхождения записываются без автоматической правки макета.

## 7. Technical JSON как источник проверки

Проверенные наборы находятся в themes/Technical(iOS)/Ui Type/:
- iPhone Compact 0-320;
- iPhone Regular 321-413;
- iPhone Wide 414+;
- iPad Compact 0-767;
- iPad Regular 768+;
- iPad Wide 1024+.

Сопоставление параметров:
- S — container.device-width либо отдельно подтверждённая входная ширина;
- L — screen-padding.left;
- R — screen-padding.right;
- N — cover.numbers.<type>;
- K — cover.gaps-count.<type>;
- W — cover.width.<type>;
- высота обложки — cover.height.<type>, с проверкой пропорции и правил округления.

Диапазоны в названиях файлов не заменяют проверку устройства, ориентации и входных данных. Платформенный набор выбирается по подтверждённому соответствию, а не только по совпадению числа в имени.

В старом JSON есть исключения и ошибки: Medium у iPhone Regular/Wide использует дополнительное gaps-count−1, а отдельная ссылка square-medium ведёт к отсутствующей высоте. Такие особенности не распространяются на все Rail и не исправляются молча в репозитории. При влиянии на результат расхождение фиксируется и разрешается отдельно.

Layout guides помогают визуальной проверке. Они не заменяют формулу и не доказывают правильность размеров всех iOS-карточек.

## 8. Выбор карточки и пропорций

| Подход | Когда применять |
|---|---|
| Rail Card iOS со стандартным Shape | Подходят общая структура и стандартная пропорция |
| Rail Card iOS, Shape=Custom | Подходит структура, нужны произвольные пропорции обложки |
| Полностью кастомная карточка | Нужны собственная структура или поведение |

Стандартные формы обложки: Horizontal 16:9, Vertical 2:3, Square 1:1 и Circle 1:1.

Для стандартной обложки:
- Horizontal: H = W × 9/16;
- Vertical: H = W × 3/2;
- Square и Circle: H = W.

Подпись, её отступы и дополнительные строки добавляются отдельно. Высота шапки не включается в размер карточки.

Rail Card сохраняет точную пропорцию обложки. В историческом Technical JSON для некоторых высот есть ceil; это отдельное правило округления источника. Оно не применяется автоматически так, чтобы нарушить пропорцию действующего мастера.

Shape=Custom позволяет независимо менять ширину и общую высоту экземпляра. При включённой подписи обложка занимает пространство за вычетом подписи и применимых отступов. Если концепт задаёт собственную пропорцию обложки, сначала рассчитывается её высота, затем добавляется область подписи.

Полностью кастомная карточка может иметь собственные пропорции. Она создаётся локально в UI Type с переиспользованием подходящих платформенных баз и общих запчастей. Нестандартное соотношение сторон само по себе не является причиной откладывать UI Type.

## 9. Скругления и тема

Для карточек Rail выбираются только скругления из системы Rail Card. Используются предусмотренные переменные rail/card/radius/*, которые получают значение активной темы.

У экземпляров сохраняются привязки мастера. У Shape=Custom и полностью кастомных карточек используется та же система скруглений Rail Card. Значение токена не копируется как фиксированное число.

Произвольные скругления и сторонние radius-токены для карточки не назначаются. При переключении темы проверяется соответствие скруглений её переменным. Circle сохраняет круглую геометрию мастера. Базовые кнопки и лейблы внутри сохраняют собственные платформенные токены.

Внутренние padding/gap карточки отличаются от промежутков карусели. Точный путь отдельного семейства Rail Card Padding Gap пока не подтверждён. У проверенного мастера Labels / padding содержит числовые 6 и 2 без привязок. До уточнения сохраняются настройки мастера; rail/gap-horizontal/* не используется вместо внутреннего токена. Незавершённая токенизация отмечается явно.

## 10. Сборка, слоты и шапка

Основной каркас — Rail Heading и Carousel внутри вертикального Auto Layout. Внутри Carousel карточки или колонки располагаются горизонтально.

Шапка и видимая область карусели используют доступную ширину, карточки — утверждённую фиксированную ширину конкретного устройства. Fill у всех карточек не должен распределять ширину между всем списком и менять плотность.

Rail Heading используется с Type=Base или Rich и подходящим Device=Phone/Tablet. Эти варианты общие для платформ. При скрытой шапке лишний промежуток до карусели не остаётся. Desktop-вариант для iOS не создаётся.

Оверлеи помещаются в слот элементов обложки, подпись — в слот подписи. Сохраняется технический слой изображения Cover. Проверяются позиции лейблов и оверлеев относительно краёв обложки.

Для обычной Rail Card используется встроенное состояние Skeleton. Дублирующие мастера скелетона не создаются. У кастомной карточки состояние загрузки определяется её композицией с переиспользованием подходящих базовых компонентов.

Высота Rail учитывает видимые элементы: шапку, интервалы, карточки, подписи и дополнительные блоки. Лишние Base Rail и одноэлементные обёртки не добавляются. Контейнеры рядов и колонок сохраняются, когда у них есть функция.

## 11. Имена и организация

- Страница: Rail <тип>.
- Компонент: Rail <тип> iOS, например Rail Main iOS.
- Варианты: пять конкретных Device из обязательного перечня.
- Запчасть: x / Rail <тип> <роль> [платформа] [размер].
- Совместимая общая запчасть не получает суффикс iOS только из-за происхождения.

Мастера лежат непосредственно на странице. Секции и дополнительные контейнеры вокруг мастеров не используются. Порядок платформ — iOS → Android → Web. Запчасти располагаются рядом с компонентом, общие сохраняются в одном экземпляре. Проверку размещай в отдельных платформенных секциях с экранными фреймами по device-review.md. Запрет секций-обёрток относится к мастерам.

## 12. Проверка готовности

Следуй проверке на устройствах: покажи связанные экземпляры на всех обязательных экранах с включёнными локальными сетками. Ошибки сообщай дизайнеру без автоматического исправления.

1. Есть все пять обязательных устройств, сохранены размеры и ориентации экранных макетов.
2. Для каждого варианта записаны утверждённый фиксированный размер карточки и его источник. При проверке по JSON отдельно записаны фактическая ширина экрана, полезная область, входная ширина S, Technical-набор, L, R, N, K, G и проверочный результат W.
3. При расхождении проверки с утверждённым размером сохранён утверждённый размер; расхождение отмечено и не вызвало автоматического пересчёта макета.
4. Количество промежутков считается через ceil(N)−1; Web-формула не подставляется.
5. Gap привязан к rail/gap-horizontal/phone или tablet; screen padding относится к iOS.
6. Выбрана стандартная Rail Card, Custom или кастомная карточка; пропорция обложки соответствует концепту.
7. Скругления взяты из системы Rail Card, привязки сохранены, темы проверены.
8. Сохранены связи с мастерами, платформенными базами, стилями и переменными.
9. Проверены все карточки, скрытые слои, оба слота, лейблы, оверлеи, подписи, состояния и индивидуальные переопределения.
10. При включении скрытых элементов и изменении размеров нет случайных наложений и обрезки текста.
11. Проверены общий заголовок, нейминг, плоская структура мастеров и расположение запчастей.
12. Все расхождения, правила округления и неподтверждённые токены перечислены отдельно.

## Android

# Принципы сборки Rail Android

Рабочая редакция от 16 ноября 2026 года. Уточнение дизайнера: межколонник Android Rail использует те же rail/gap-horizontal/*, что и межкарточный интервал: Phone 6, Tablet 8. Документ основан на решениях из чата, текущей библиотеке UI Type, измерениях Android-источника и проверенных токенах. Описание правил не означает автоматическую готовность всех исторических UI Type.

## 1. Состав Rail и исходный концепт

Rail — готовая композиция UI Type: общий заголовок, карусель и карточки. Фон, дополнительные изображения, навигация, спонсорские и другие блоки подключаются по концепту.

До сборки определяются повторяемая единица, число рядов, содержание карточки, пропорции обложки и поведение подписи. Повторяемой единицей может быть карточка или колонка из нескольких карточек. У двухрядного Rail горизонтально рассчитывается ширина колонки, вертикально — обе карточки и промежуток между ними.

При воспроизведении существующего типа изучаются все исходные карточки, включая скрытые слои, состояния и индивидуальные переопределения. Названия типа недостаточно для определения его устройства.

## 2. Источники компонентов

- Основной компонент карточки — локальный Rail Card Android в библиотеке UI Type.
- Заголовок — общий Rail Heading из этой же библиотеки.
- Базовые Label, Rich Label, кнопки и другие платформенные элементы — из Lib-Android-Mobile или подтверждённой общей базовой библиотеки.
- Уникальные запчасти создаются в библиотеке UI Type рядом с соответствующим Rail.
- Совместимые запчасти переиспользуются между типами и платформами. Разница только в ширине не является причиной создавать новый мастер.
- При переиспользовании проверяются состав, свойства, типографика, токены, состояния и базовые зависимости.

Экземпляры сохраняют связи с мастерами. Базовые компоненты не заменяются нарисованными копиями. Наличие общего заголовка или общей подписи не разрешает автоматически использовать неподходящие iOS/Web-базовые компоненты.

Lib-Android-Mobile служит источником для изучения и переиспользования. Правки исходной платформенной библиотеки не входят в обычную сборку Rail в UI Type.

## 3. Три обязательных макета

| Вариант Rail | Ширина экрана S, px | Screen padding P с каждой стороны, px | Полезная ширина A, px | Колонок C | Gutter сетки g, px | Gap карточек G, px |
|---|---:|---:|---:|---:|---:|---:|
| Device=Phone | 360 | 16 | 328 | 8 | 8 | 6 |
| Device=Tablet P | 640 | 24 | 592 | 12 | 12 | 8 |
| Device=Tablet L | 1024 | 24 | 976 | 12 | 12 | 8 |

Phone работает в портретной ориентации; поворот телефона заблокирован. Вариант Phone Landscape не создаётся. Планшет обязательно проверяется в Portrait и Landscape.

Это размеры макетов Figma в px. Android-реализация использует dp и адаптируется к доступному пространству. Три ширины макетов не означают три физических разрешения устройств или три неизменных размера карточек в приложении. Произвольный коэффициент перевода px в dp не вводится.

У Rail Card и Rail Heading используются Device=Phone и Device=Tablet. Общий внутренний Tablet-компонент не заменяет два геометрических варианта самого Rail.

Для построения доступны нативные Layout guide styles Android/Phone — 8 колонок, padding 16 и gutter 6; Android/Tablet — 12 колонок, padding 24 и gutter 8. Один Tablet-стиль используется на 640 и 1024 и растягивается вместе с фреймом. Guides применяются к фрейму полной ширины экрана. Специальная правая расчётная полоса для Android не добавляется. Gutter guides и gap между карточками имеют разные роли, но привязываются к одним rail/gap-horizontal/phone=6 и tablet=8.

## 4. Полезная область и screen padding

A = S − 2 × P

P берётся из отдельных Android-токенов:
- screen-padding/android/phone = 16;
- screen-padding/android/tablet = 24.

Для Android не вводится специальный правый расчётный отступ R из моделей iOS или Web. Положение и размеры карточек определяются сеткой, концептом и подтверждёнными платформенными образцами.

У обычного Rail видимая область и ширина шапки соответствуют A. Корень фоновой или составной композиции может иметь полную ширину S. Перед назначением отступов проверяется, не ограничил ли родитель полезную область: screen padding не вычитается повторно.

## 5. Формула размера по колонкам

Для карточки, которая по концепту занимает целое число колонок сетки:

Ширина колонки = (полезная ширина − ((количество колонок − 1) × gutter сетки)) / количество колонок.

Ширина карточки = (занимаемые колонки × ширина колонки) + ((занимаемые колонки − 1) × gutter сетки).

Обозначения для агента:

columnWidth = (A − (C − 1) × g) / C
cardWidth = span × columnWidth + (span − 1) × g

span определяется концептом или подтверждённым источником. Сетка не доказывает, что любая историческая карточка должна занимать целое число колонок.

Пример Phone Main:
A = 360 − 2 × 16 = 328;
columnWidth = (328 − 7 × 6) / 8 = 35,75;
span = 5;
cardWidth = 5 × 35,75 + 4 × 6 = 202,75 px.

Пример Tablet Landscape Main:
A = 1024 − 2 × 24 = 976;
columnWidth = (976 − 11 × 8) / 12 = 74;
span = 3;
cardWidth = 3 × 74 + 2 × 8 = 238 px.

На Tablet Portrait Main при span=4 новая модель с g=8 даёт 192 px. Исторические фиксированные размеры Main — Phone 202, Tablet P 189 и Tablet L 235 px — не пересчитываются автоматически. Расхождения 202,75/192/238 с ними фиксируй для дизайнера; это не общее правило округления. Общий ceil или floor для всех Android-карточек не вводится.

## 6. Gutter сетки и gap карусели

g и G имеют разные роли:

- g = 6/8 — расстояние между колонками сетки, участвует в расчёте columnWidth и span;
- G = 6/8 — фактическое расстояние между карточками карусели.

Для карусели назначаются локальные переменные библиотеки UI Type:
- rail/gap-horizontal/phone = 6;
- rail/gap-horizontal/tablet = 8.

Оба свойства привязываются к одной существующей переменной Rail Gap соответствующего устройства. Не используй отдельные spacing/150 или spacing/200 для межколонника Rail.

Если концепт задаёт собственную композицию или отличается от исторического Rail, решение фиксируется отдельно. Старые интервалы исходной библиотеки не становятся общим правилом новой сборки. Например, в текущем Rail Catalog Android интервалы уже приведены к 6/8.

## 7. Три подхода к карточке

| Подход | Когда применять |
|---|---|
| Rail Card Android со стандартным Shape | Подходят структура и стандартная пропорция |
| Rail Card Android, Shape=Custom | Подходит структура, нужны произвольные пропорции обложки |
| Полностью кастомная карточка | Нужны собственная структура или поведение |

Стандартные формы обложки: Horizontal 16:9, Vertical 2:3, Square 1:1, Circle 1:1.

У Shape=Custom ширина и общая высота экземпляра независимы. При включённой подписи высота экземпляра включает и обложку, и подпись: обложка занимает оставшееся пространство. Если концепт задаёт конкретную пропорцию обложки, сначала рассчитывается её высота, затем добавляется область подписи и применимые интервалы.

У полностью кастомной карточки допустимы собственные пропорции. Она хранится локальным мастером в UI Type, переиспользует подходящие платформенные базы и общие запчасти. Нестандартное соотношение сторон само по себе не является причиной откладывать UI Type.

Ширина вложенной картинки не обязательно равна ширине повторяемой карточки. Для составных строк и блоков эти величины описываются отдельно.

## 8. Высота и текущие фиксированные примеры

Пропорция относится к обложке:
- Horizontal: H = W × 9/16;
- Vertical: H = W × 3/2;
- Square и Circle: H = W.

Подпись, её отступы и дополнительные строки учитываются отдельно. Высота шапки не включается в размер карточки.

Текущие примеры, которые нельзя молча подгонять под другое правило:
- Main Android: Phone W=202, Tablet P W=189, Tablet L W=235.
- Continue и Background переиспользуют ширины Main; у Continue есть подпись.
- Large Phone: утверждённая ширина 289, обложка приведена к 16:9 — 289 × 162,5625. Ширина не заменяется на другое значение сетки без отдельного решения по концепту.
- Highlights Sport Phone: квадратная обложка 328 × 328, подпись под ней; планшетные обложки используют 16:9.
- Circle: аватары 88 на Phone и 112 на обоих планшетных макетах.
- Catalog: общая планшетная карточка шириной 189 сохранена на обоих планшетных макетах.

Это примеры конкретных семейств, а не размеры всех Android Rail.

## 9. Скругления и тема

Для карточек Rail выбираются только скругления из системы Rail Card. Используются предусмотренные переменные rail/card/radius/*, которые получают значение активной темы.

У экземпляров Rail Card сохраняются привязки мастера. У Shape=Custom и полностью кастомных карточек используется та же система скруглений Rail Card. Текущее числовое значение токена не копируется в виде фиксированного radius.

Произвольные скругления и сторонние radius-токены для карточки не назначаются. При переключении темы проверяется соответствие скруглений значениям её переменных. Circle сохраняет круглую геометрию мастера. Базовые кнопки и лейблы внутри сохраняют собственные платформенные токены.

Внутренние padding/gap карточки отличаются от интервалов между карточками. Точный путь отдельного семейства Rail Card Padding Gap пока не подтверждён. У проверенного мастера Labels / padding содержит числовые 6 и 2 без привязок. До уточнения сохраняются настройки мастера; rail/gap-horizontal/* не используется вместо внутреннего токена. Незавершённая токенизация отмечается явно.

## 10. Сборка, слоты и шапка

Основной каркас собирается вертикальным Auto Layout: Rail Heading и Carousel. Внутри Carousel карточки или колонки располагаются горизонтально.

Шапка и карусель растягиваются по доступной ширине, карточки получают рассчитанную или утверждённую ширину. Fill у всех карточек не должен распределять ширину между всем списком и менять композицию.

Rail Heading используется с Type=Base или Rich и Device=Phone/Tablet. Эти варианты шапки общие для платформ. Если шапка скрыта, лишний промежуток до карусели не остаётся.

Оверлеи находятся в слоте элементов обложки, подписи — в слоте подписи. Сохраняется технический слой изображения Cover. Оверлеи проверяются на правильную привязку к краям при ресайзе.

Для обычной Rail Card применяется встроенное состояние Skeleton. Дублирующие мастера скелетона не создаются. У кастомных карточек состояние загрузки определяется их композицией с переиспользованием подходящих базовых компонентов.

Высота Rail учитывает шапку, интервалы, карточки, подписи и дополнительные блоки. Лишние Base Rail и одноэлементные обёртки не добавляются. Контейнеры рядов и колонок сохраняются, если у них есть функция.

## 11. Имена и размещение

- Страница: Rail <тип>.
- Компонент: Rail <тип> Android, например Rail Main Android.
- Варианты: Device=Phone, Device=Tablet P, Device=Tablet L.
- Запчасть: x / Rail <тип> <роль> [платформа] [размер].
- Совместимая общая запчасть не получает суффикс Android только из-за места использования.

Мастера лежат непосредственно на странице. Секции и дополнительные контейнеры вокруг мастеров не используются. Платформы стоят в ряд iOS → Android → Web; запчасти находятся рядом, общие сохраняются в одном экземпляре. Проверку размещай в отдельных платформенных секциях с экранными фреймами по device-review.md. Запрет секций-обёрток относится к мастерам.

## 12. Проверка готовности

Следуй проверке на устройствах: покажи связанные экземпляры на всех обязательных экранах с включёнными локальными сетками. Ошибки сообщай дизайнеру без автоматического исправления.

1. Есть Phone 360, Tablet Portrait 640 и Tablet Landscape 1024; Phone Landscape отсутствует.
2. Для каждого варианта записаны размеры экрана и области, модель размера карточки, исходник и правило округления.
3. В сеточной модели указаны C, g и span; gutter и G карусели используют один Rail Gap 6/8; роли параметров различаются.
4. Screen padding относится к Android, gap — к локальным rail/gap-horizontal/*.
5. Выбрана стандартная Rail Card, Custom или кастомная карточка; пропорции соответствуют концепту.
6. Скругления взяты из системы Rail Card, привязки сохранены, темы проверены.
7. Сохранены связи с мастерами, платформенными базами, стилями и переменными.
8. Проверены все карточки, скрытые слои, оба слота, лейблы, оверлеи, подписи, состояния и индивидуальные переопределения.
9. При изменении размера нет случайных наложений и обрезки текста; намеренные обрезка и сокращение соответствуют концепту.
10. Проверены общая шапка, нейминг, расположение компонентов и запчастей.
11. Все исключения и неподтверждённые параметры перечислены отдельно.

## Web

# Принципы сборки Rail Web

Рабочая редакция от 13 ноября 2026 года. Основана на решениях из чата, текущих компонентах библиотеки UI Type и проверенных токенах. Документ описывает правила сборки; он не означает, что все исторические компоненты уже полностью им соответствуют.

## 1. Rail — готовая композиция UI Type

Rail включает заголовок, карусель и её содержимое. По концепту могут добавляться навигация, фон, спонсорский блок и другие элементы.

Повторяемой единицей может быть отдельная карточка или колонка из нескольких карточек. Это нужно определить до расчёта размеров. У двухрядного Rail горизонтальное количество N относится к колонкам; вертикальные интервалы рассчитываются отдельно.

Исходный концепт задаёт содержание, композицию, поведение и плотность карточек. При воспроизведении существующего типа проверяются все исходные карточки, включая скрытые слои и индивидуальные переопределения.

## 2. Выбор карточки

Предусмотрены три подхода.

| Подход | Когда применять |
|---|---|
| Rail Card Web, стандартный Shape | Подходит общая структура карточки и одно из стандартных соотношений сторон |
| Rail Card Web, Shape=Custom | Подходит общая структура, нужны произвольные пропорции обложки |
| Полностью кастомная карточка | Самостоятельная композиция или поведение, которые не укладываются в Rail Card |

У стандартной Rail Card доступны Horizontal 16:9, Vertical 2:3, Square 1:1 и Circle 1:1. Соотношение относится к обложке, а не к карточке вместе с подписью.

Для Shape=Custom ширина и общая высота экземпляра независимы. При включённой подписи обложка занимает оставшееся место: высота обложки = общая высота карточки − высота области подписи − применимые промежутки и отступы. Если концепт задаёт обложку 4:5, сначала рассчитывается её высота по этой пропорции, затем добавляется подпись.

У кастомной карточки разрешены собственные пропорции. Нестандартное соотношение сторон не является основанием исключать UI Type из сборки. Мастер кастомной карточки хранится в библиотеке UI Type рядом с соответствующим Rail.

## 3. Источники компонентов

- Rail Card Web и Rail Heading берутся из библиотеки UI Type.
- Label, Rich Label, кнопки и другие базовые компоненты берутся из Lib-Web или подтверждённой общей базовой библиотеки.
- Уникальные запчасти конкретного Rail создаются в библиотеке UI Type.
- Совместимые общие запчасти переиспользуются между типами и платформами. Разница только в ширине не требует нового мастера.
- При переиспользовании проверяются состав, типографика, токены, состояния и библиотечные зависимости.
- Экземпляры сохраняют связь с мастерами. Базовые компоненты не заменяются нарисованными копиями.

## 4. Обязательные брейкпойнты

Для полной Web-сборки нужен один компонентный набор с шестью вариантами свойства breakpoint: 320, 375, 768, 1024, 1440 и 1920. Web включает мобильные, планшетные и десктопные размеры.

| Брейкпойнт, px | Device карточки и шапки | Screen padding L, px | Правый расчётный R, px | Gap G, px | Токен интервала |
|---:|---|---:|---:|---:|---|
| 320 | Phone | 12 | 36 | 6 | rail/gap-horizontal/phone |
| 375 | Phone | 12 | 36 | 6 | rail/gap-horizontal/phone |
| 768 | Tablet | 32 | 56 | 8 | rail/gap-horizontal/tablet |
| 1024 | Tablet | 32 | 56 | 8 | rail/gap-horizontal/tablet |
| 1440 | Desktop | 56 | 56 | 8 | rail/gap-horizontal/tablet |
| 1920 | Desktop | 72 | 72 | 10 | rail/gap-horizontal/desktop |

Screen padding соответствует отдельным Web-токенам:
- 320/375 — screen-padding/web/mobile;
- 768/1024 — screen-padding/web/tablet;
- 1440 — screen-padding/web/desktop-m;
- 1920 — screen-padding/web/desktop-l.

Device и токен интервала выбираются отдельно. На 1440 Device=Desktop, а gap=8 через tablet-токен. Слово Desktop само по себе не означает gap=10.

L и G подтверждены токенами и текущим Rail Main Web. Значения R восстановлены по геометрии стандартных семейств; отдельный Web Technical-токен R в проверенных источниках не найден. Это рабочая таблица стандартных Rail. Особую геометрию конкретного концепта, включая Highlights и Announces, нужно описывать отдельно.

Для построения доступны нативные Layout guide styles: Web/Mobile (320, 375) — общий для 320, 375 и других Mobile-ширин с теми же параметрами; Web/Tablet (768, 1024) — общий для 768 и 1024; Web/Desktop M (1440) — для 1440; Web/Desktop L (1920) — для 1920. Над Web-примерами дополнительно указаны подписи breakpoint=320, breakpoint=375, breakpoint=768, breakpoint=1024, breakpoint=1440 и breakpoint=1920. Desktop разделён из-за различий padding и gap. Стиль применяется к фрейму полной ширины экрана, а не к уже уменьшенной полезной области Rail. Колонки растягиваются вместе с фреймом. Показаны 12 вспомогательных колонок и красная полоса полного правого расчётного отступа R; число колонок guides не заменяет расчёт карточек через N.

Шесть размеров являются опорными макетами. Они сами по себе не определяют все правила между ними: границы переключения типографики, токенов и плотности должны быть заданы правилами адаптивности конкретного Rail. Layout guide style не переключается между группами автоматически при ресайзе.

## 5. Три разные ширины

S — ширина экрана или согласованного внешнего контейнера. В примерах ниже используется ширина экрана.

Для стандартного Rail:
- L — левый screen padding;
- P — обычный правый screen padding, равный L;
- R — полный правый расчётный отступ от края экрана;
- B = S − L − P — видимая ширина Rail;
- A = S − L − R — область, по которой рассчитывается ширина карточек.

На мобильных и планшетных макетах R больше screen padding на 24 px. На 1440 и 1920 R равен screen padding.

R уже включает отступ от края экрана. К нему не нужно повторно прибавлять screen padding. R также не следует автоматически назначать как paddingRight карусели.

Например, на 375:
- ширина экрана S = 375;
- видимая ширина Rail B = 375 − 12 − 12 = 351;
- расчётная область A = 375 − 12 − 36 = 327.

Заголовок и видимая область карусели здесь имеют ширину 351. Карточки рассчитываются по области 327. Эти две области не нужно уравнивать.

У Rail с фоном или сложной композицией внешний корень может иметь другую ширину. Отступы нельзя вычитать повторно, если родитель уже ограничил полезную область.

## 6. Формула ширины карточки

W = (S − L − R − ((N − 1) × G)) / N

Где:
- W — ширина повторяемой карточки или колонки;
- S — ширина экрана;
- L — левый screen padding;
- R — полный правый расчётный отступ;
- G — интервал между карточками;
- N — расчётное количество карточек или колонок в области A.

Сначала из ширины экрана вычитаются левый и правый расчётные отступы. Затем вычитаются промежутки: (N − 1) × G. Остаток делится на N.

N задаётся отдельно для каждого типа и брейкпойнта до расчёта W. Не подгоняй N обратной формулой под пиксельную ширину концепта ради видимости правильного расчёта; если плотность не задана и не подтверждена подходящим семейством, уточни её у дизайнера. Оно может быть дробным. Для текущих стандартных Web-семейств используется непрерывная формула N − 1, без ceil и без переноса правила iOS. При дробном N это расчётный коэффициент плотности, а не обещание буквального количества видимых карточек на всём экране.

Пример Rail Main на 1024:
W = (1024 − 32 − 56 − ((4 − 1) × 8)) / 4 = 228 px.

Пример текущего Rail Main на 375:
N = 5/3;
W = (375 − 12 − 36 − (((5/3) − 1) × 6)) / (5/3) = 193,8 px.

Эти значения N подтверждают геометрию Main и не становятся общими значениями для всех Rail.

Сохраняется точность вычисления. Для показа результата допустимо округление до двух знаков; промежуточные вычисления и дробное N не округляются автоматически до целых.

Для сложной кастомной композиции сначала определяется ширина повторяемого блока. Размер вложенного изображения не следует автоматически принимать за ширину карточки.

## 7. Высота карточки и Rail

Для стандартных пропорций:
- Horizontal: высота обложки = W × 9/16;
- Vertical: высота обложки = W × 3/2;
- Square и Circle: высота обложки = W.

Подпись и её отступы добавляются отдельно. Высота шапки не входит в высоту карточки.

У Rail высота складывается из видимых элементов композиции: шапки, интервала до карусели, высоты карусели и дополнительных блоков. Скрытая шапка не должна оставлять пустой промежуток.

В двухрядном типе учитываются высота обеих карточек, их подписи и вертикальный интервал. Горизонтальный gap не используется вместо вертикального автоматически.

- Для изображения сохраняется технический слой Cover.
- Слоты элементов и подписи используются по назначению.
- Состояние Skeleton берётся из Rail Card; отдельные дубли скелетона для обычной Rail Card не создаются.
- Лишние Base Rail и одноэлементные обёртки не добавляются. Контейнеры рядов и колонок сохраняются, когда у них есть функция.

В Figma ширины карточек на опорных брейкпойнтах задаются расчётом. Наличие Auto Layout не означает, что формула N уже автоматически выполняется при произвольном ресайзе. Адаптивный пересчёт для разработки описывается явно.

## 9. Шапка и навигация

Используется общий компонент Rail Heading с Type=Base или Rich и подходящим Device.

Для Phone и Tablet сохраняются общие платформенные варианты шапки. Для Desktop используется его собственный размер типографики и изображений; правая стрелка перехода в шапке скрыта.

Стрелка шапки и управление прокруткой карусели — разные элементы. Скрытая стрелка Desktop-шапки не означает удаление кнопок навигации карусели.

Навигация, изображения и дополнительные блоки подключаются по концепту из существующих компонентов. Собственные копии базовых иконок и кнопок не рисуются.

## 10. Токены

Интервалы между карточками привязываются к локальным rail/gap-horizontal/* в библиотеке UI Type. Значение назначенного токена должно совпадать с G в формуле.

Для карточек Rail выбираются только скругления, предусмотренные системой Rail Card. Они привязаны к переменным rail/card/radius/* и могут менять значение в зависимости от темы. Выбор скругления означает выбор соответствующего компонентного токена, а не копирование его текущего числового значения.

У экземпляров Rail Card сохраняются привязки мастера. У Shape=Custom и полностью кастомных карточек используется та же система скруглений Rail Card; произвольные значения и сторонние radius-токены не назначаются. При переключении темы скругления должны обновляться через переменные без ручной правки каждого Rail. У формы Circle сохраняется круглая геометрия мастера. Вложенные кнопки и лейблы сохраняют собственные платформенные токены.

Screen padding берётся из Web-семейства, а не из iOS или Android.

Внутренние padding и gap карточки нужно отличать от gap карусели. Точное имя отдельного семейства Rail Card Padding Gap пока не подтверждено. В проверенном Rail Card Web у Labels / padding сейчас стоят числовые значения 6 и 2 без соответствующих привязок. Их нельзя выдавать за подтверждённые компонентные токены или использовать rail/gap-horizontal/* как замену. До уточнения сохраняются настройки мастера; незавершённая токенизация отмечается явно.

## 11. Имена и организация библиотеки

- Страница: Rail <тип>.
- Компонент Web: Rail <тип> Web, например Rail Main Web.
- Варианты: breakpoint=320, breakpoint=375 и остальные согласованные значения.
- Запчасть: x / Rail <тип> <роль> [платформа] [размер], например x / Rail Continue Slot Caption Web Desktop L.
- Общая запчасть не получает платформенный суффикс без необходимости.

Основные компоненты доступны прямо на странице. Секции и дополнительные контейнеры вокруг мастеров не используются. Порядок платформ слева направо: iOS, Android, Web. Запчасти находятся рядом с соответствующим компонентом, общие — в одном экземпляре. Проверку размещай в отдельных платформенных секциях с экранными фреймами по device-review.md. Запрет секций-обёрток относится к мастерам.

Rail — название типа композиции. Общий префикс UI Type не добавляется: для будущего Grid будет использоваться своё название.

## 12. Проверка готовности

Следуй проверке на устройствах: покажи связанные экземпляры на всех обязательных экранах с включёнными локальными сетками. Ошибки сообщай дизайнеру без автоматического исправления.

Rail Web готов к передаче, когда:

1. Собраны все шесть брейкпойнтов; любое исключение описано явно.
2. Для каждого варианта записаны S, L, R, G, N, ширина и пропорции обложки.
3. Выбран правильный подход: стандартная Rail Card, Custom или кастомная карточка.
4. Сохранились связи с мастерами, базовыми компонентами, стилями и переменными. Скругления карточек взяты только из системы Rail Card; их привязки сохранены и изменение при переключении темы проверено.
5. Проверены все карточки, скрытые слои, состояния, содержимое обоих слотов и индивидуальные переопределения.
6. Лейблы, оверлеи, скелетон и подписи работают при изменении размеров.
7. Нет случайной обрезки текста и наложений; намеренные обрезка и сокращение текста соответствуют концепту.
8. Проверены шапка Desktop, навигация, внешний вид и доступная область карусели.
9. Соблюдены нейминг, плоская структура мастеров и расположение запчастей.
10. Предположения, исключения и неподтверждённые токены перечислены отдельно.

## Слоты и Custom при программном редактировании

# Rail Card: проверенная механика Figma

Наблюдения от 13 ноября 2026. Применяй только к соответствующим мастерам, сверяя текущий API и структуру. Это инструкция для изменений карточки, не требование перестраивать работающие узлы.

## Скрытые слои и свойства

Для полного обхода экземпляров устанавливай figma.skipInvisibleInstanceChildren = false. Читай свойства родительского COMPONENT_SET; componentPropertyDefinitions недоступен на отдельном variant-компоненте.

В Rail Card есть два настоящих SLOT: элементы поверх обложки и подпись. Вариант Shape=Custom сохраняет оба слота и существующие boolean-свойства. Не заменяй SLOT простым FRAME.

## Клонирование

В проверенном API clone отдельного component превращал SLOT в FRAME и терял componentPropertyReferences у дочерних слоёв. Клонирование всего набора сохраняло слоты. После любой операции фактически проверь тип узлов и привязки.

При восстановлении слотов через createSlot:
- перенеси исходные componentPropertyReferences и содержимое;
- восстанавливай boolean-привязки внутри компонента, не заходя в независимые вложенные INSTANCE;
- скопируй fills и strokes: новый SLOT по умолчанию может иметь белую заливку;
- убери только созданные этой операцией лишние SLOT-свойства.

Не удаляй оригинальные свойства и узлы до проверки восстановления.

## Shape=Custom

Рабочая структура: корень с фиксированными шириной/высотой; Cover без aspect-ratio lock, FILL по обеим осям; слот подписи HUG. Меняй полную ширину и высоту экземпляра, чтобы задать свободную пропорцию. При видимой подписи её высота вычитается из общей.

Прямой resize вложенного Cover внутри instance в проверке не менял его высоту. Не объявляй такую операцию рабочей без проверки реального размера. Настройка HUG у корня с FIXED Cover — отдельная модель, а не обязательная замена свободного ресайза.
