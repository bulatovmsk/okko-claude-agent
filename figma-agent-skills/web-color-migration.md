# Миграция цветов Okko Web

Выполни миграцию в области, указанной пользователем, и докажи результат полным повторным аудитом. Количество выполненных замен само по себе не доказывает завершение. Общайся с пользователем по-русски.

## Обязательные правила

- Меняй только мастер-компоненты `COMPONENT` и принадлежащие им обычные слои. Контейнер `COMPONENT_SET`, оформление страницы, гайды и примеры вне мастеров не являются разрешёнными целями записи.
- Не меняй вложенные `INSTANCE`, их собственные заливки, overrides или потомков. Не делай detach, reset overrides или swap. Их мастера будут обработаны отдельно. Чтение инстансов для аудита обязательно.
- По умолчанию не меняй детские компоненты и варианты Kids, а также light. Пользователь разрешил исключение для пяти соответствий в таблице «Разрешённые замены light/Kids»: их применяй и внутри light/Kids-мастеров. Остальные источники в этих поддеревьях не меняй. Не отсекай всё поддерево до проверки этих пяти соответствий. Проверяй свойства, имя мастера, component set, предков и режимы переменных. Учитывай обозначения `Theme=Light`, `Фон=Светлый`, `Цвет=Светлый`, `Тёмный/Темный фон=False/Off`, `On Dark=false`, «На светлом», `Kids`, «Детское». Не ограничивайся одной регуляркой или английским свойством Theme. При неясной теме отложи конкретную цель и уточни.
- Цвет без стиля и без привязки к переменной не трогай. Наличие старого paint style считается существующей цветовой привязкой, даже если его paints содержат числовой RGB. Не путай такой стиль с raw-цветом слоя.
- Не создавай переменные, токены, aliases, коллекции или дубликаты — даже временные. Разрешён импорт существующей библиотечной переменной или стиля. Не создавай новый стиль для обхода отсутствующего токена.
- Не редактируй определения общих стилей и переменных: заменяй привязки только у разрешённых слоёв. Не меняй геометрию, тексты, свойства, состояния, темы, opacity слоя, режимы коллекций и структуру компонентов.
- Не расширяй область записи по найденным зависимостям. Ссылка на страницу разрешает работу с её мастерами; ссылка на компонент — только с ним. Ссылка на инстанс не разрешает незаметно перейти к редактированию его мастера в другом месте.
- Однозначные замены выполняй без дополнительного разрешения. Неоднозначную замену выполняй только после ответа пользователя: покажи старый цвет, контекст, существующие кандидаты и рекомендацию. Молчание, новая ссылка или «продолжай» без ясного выбора не утверждают спорное соответствие.

## 1. Зафиксируй область и исходное состояние

Открой актуальную ссылку и проверь имя, тип и ID цели. Не используй из памяти прошлую ветку или ноды. Для замен используй согласованную таблицу из этой инструкции, проверяя существование актуальной цели. Используй документированные средства чтения и записи Figma-агента.

До записи прочитай контракт аудита в конце этой инструкции. Собери две области:

1. **Область чтения:** всё поддерево цели, включая скрытые слои, light, Kids и все уровни инстансов.
2. **Область записи:** только разрешённые мастера и их собственные слои с известной темой, без исключённых поддеревьев.

Зафиксируй найденные источники цветов до замены: style ID/key/name, variable ID/key/name/collection/mode, поле и диапазон текста, node ID, мастер, путь и причину исключения. Проверь fills, strokes, цветные effects, градиенты и текстовые диапазоны. Не ограничивайся `boundVariables`: большая часть Deprecated может быть в paint styles.

Не исключай мастера из аудита лишь потому, что они скрытые или лежат в блоке «старое/не используем». Их наличие и область работы должны быть отражены явно; не удаляй их и не объявляй актуальными.

## 2. Найди реальные соответствия

`[Deprecated]` обозначает старые цвета; актуальные решения ищи среди существующих `color`/`Color`. Проверяй **и переменные, и paint styles** в доступных библиотеках и файле. Градиент может быть актуальным стилем, которого нет в списке переменных. Перед выводом «замены нет» проверь оба источника.

Имя не является единственным доказательством. Проверяй библиотеку, collection ID, key, назначение, тип заливки и актуальную опубликованную сущность. Старая привязка может называться `color/...`, но ссылаться на старую коллекцию/версию. Совпадение RGB не доказывает семантическое соответствие. Если доступен канонический источник токенов проекта, сверяй спорные значения с ним read-only; при конфликте не выбирай источник молча.

Составь таблицу `источник → существующая цель → назначение → число применений → основание → статус`. Статусы: однозначно, согласовано пользователем, требует согласования, подходящей цели нет.

Согласованные строки таблиц ниже применяй сразу, без повторного согласования. Разрешены указанные переходы градиента к переменной, включая Decorative Focus и Continuum/Lighthouse. Для источников вне таблиц подбирай существующий семантический color по назначению слоя, а не по совпадению RGB. Однозначный выбор применяй, неоднозначный согласовывай. Даже стиль текста, применённый к фону целого мастера, требует проверки контекста. Brand/Partners/Sber явно отложен: не заменяй его на sber-button.

Для light/Kids выполняй только пять явно разрешённых соответствий ниже; остальные сохраняй. Если тема слоя неоднозначна, выясняй тему, а не согласовывай заведомо запрещённую замену.

## 3. Выполни замену

Перед каждым пакетом заново проверь, что цели существуют, не стали инстансами, разрешены общими правилами либо одним из пяти исключений light/Kids и всё ещё используют ожидаемый старый источник. Записывай только таблицу однозначных и явно согласованных замен.

Сохраняй остальные paints, эффекты, диапазоны, градиентные позиции/трансформации и прозрачность слоя. При переходе от стиля к переменной корректно убери старую связь со стилем и привяжи существующую переменную. При переходе к актуальному градиентному стилю применяй существующий стиль. Превращать градиент в solid разрешено только для явно согласованных в таблице переходов к переменной; меняй цветовое оформление целиком, сохраняя геометрию и opacity слоя. Не запекай переменную в HEX/RGB.

У текста проверяй все оформленные диапазоны. Не присваивай единую заливку всему тексту с разными цветами. Загружай фактические шрифты перед изменениями, если этого требует API.

Пакеты подбирай по фактической длительности. Возвращай ID всех изменённых узлов и результат проверки. При тайм-ауте сначала прочитай фактическое состояние конкретного пакета, затем повтори только несохранённую часть. Не запускай повторную запись поверх неизвестного состояния.

Храни журнал вне Figma: область, выполненные пакеты, соответствия, согласования и остатки. Не записывай служебный журнал в descriptions компонентов, plugin data или новые ноды.

## 4. Проверь весь результат

Повторно прочитай **всю исходную область чтения**, а не только изменённые ноды и не только прямых детей мастеров. Сопоставь каждый оставшийся старый источник с конкретными узлами и причинами из контракта аудита.

Если доступен UI, проверь Selection colors для той же области и разберите каждую запись `[Deprecated]`. Если UI недоступен, используй полный программный аудит и прямо укажи, что это эквивалентная проверка источников, а не просмотр панели. Не утверждай, что открыл Selection colors, если этого не было.

Проверь сохранение исключённых слоёв и отсутствие непредусмотренных записей. Изменение вида инстанса вследствие разрешённой правки его мастера отличается от прямой записи в инстанс; учитывай это при сравнении.

Если пропущенная привязка разрешена и её замена однозначна — исправь и перепроверь затронутую область. Если есть неоднозначность — задай вопрос с конкретными кандидатами и ссылкой на пример. Если обход неполный, есть ошибки чтения или необъяснённые остатки, статус — **проверка не завершена**.

## Результат пользователю

Кратко сообщи:

- какая область проверена и сколько привязок/узлов изменено;
- сколько старых применений осталось по причинам: light, Kids, инстансы, вне мастеров, ожидают согласования, нет подходящего решения;
- конкретные спорные замены, по которым нужен ответ, со ссылками на примеры;
- любые непрочитанные участки и ограничения проверки.

«Миграция разрешённой области завершена» допустимо только когда полный обход окончен, все однозначные разрешённые замены подтверждены, необъяснённых остатков нет. При ожидающем согласовании скажи, что выполнена только однозначная часть. Ноль старых цветов на всей странице не является целью, если light/Kids/инстансы намеренно сохраняются.


# Контракт полного аудита цветов

## Что считать применением

Единица учёта — источник цвета в определённом поле узла или диапазоне текста. Различай число применений, уникальных узлов и уникальных источников. Не выдавай одно за другое.

Минимальная запись:

```text
fileKey, pageId, scopeId
nodeId, nodePath, masterId, instanceAncestorId
field, paintIndex, textRange?, gradientStopIndex?
sourceKind: paint-style | variable | raw | unresolved
sourceId, sourceKey, sourceName, collectionId?, collectionName?, mode?
flags: light, kids, insideInstance, outsideMaster, hidden
decision, reason, targetId?, targetName?, approvalEvidence?
```

Сохраняй все flags, даже если для итогового подсчёта выбрана одна основная причина. Для непересекающейся сводки используй приоритет: Kids → light → инстанс → вне мастера → разрешённый мастер. Не определяй тему исключительно по имени цветового стиля: `on Light` — сигнал проверить контекст, а не доказательство свойства темы.

## Обход

1. Зафиксируй точный набор корневых нод. Для страницы получи полный список верхнего уровня, включая скрытые ноды. Деление на пакеты должно покрывать этот список без пропусков и двойного счёта.
2. В read-only обходе заходи внутрь каждого INSTANCE, включая скрытых потомков. Передавай контекст предков: мастер, ближайший инстанс, light/Kids. Сохраняй причины отдельно от решения, разрешена ли запись.
3. Проверяй fillStyleId, strokeStyleId, цветные effect styles, bindings paints/effects, gradient stops и смешанное оформление текста. Одновременно учитывай собственные свойства инстанса и свойства его потомков.
4. Для текста читай диапазоны, если общий fillStyleId **или fills** смешанные; неоднородный цвет может существовать без смешанных style ID. Не считай одинаковую привязку дважды через node-level и range-level данные.
5. Проверяй прямую переменную и её принадлежность актуальной коллекции. Alias-chain можно читать для проверки источника и значения; ссылки внутри определения переменной не являются дополнительными применениями на холсте.
6. Векторные области и другие поддерживаемые API источники отдельных заливок тоже входят в аудит. Если инструмент не раскрывает какое-либо поле, укажи его как непроверенное, а не как чистое.
7. Стили разрешай по уникальным ID с кешем на запрос, а не повторно на каждом слое. Сохраняй разные версии одного key, пока не доказано, что это один источник. Не теряй отсутствующие/неразрешимые ссылки.

Не вызывай небезопасный getter variantProperties у компонента с ошибками набора без обработки ошибки. Используй доступные определения и имена, фиксируй неопределённость. Если тема не установлена уверенно и замена не входит в пять разрешённых для light/Kids соответствий, запись запрещена до выяснения; остальной аудит продолжается.

## Отдельный проход записи

Read-only обход и выбор целей записи — разные операции. В проходе записи INSTANCE является жёсткой границей: не записывай ни сам узел, ни его потомков, даже когда аудит нашёл там Deprecated. Найденный master другого компонента записывай только если он сам находится в текущей разрешённой области и прошёл проверку темы.

Для каждого пакета сохрани до записи старую привязку и изменяемые свойства. Проверка после записи должна подтвердить ожидаемый target ID/style ID и отсутствие старой связи, а не только равенство RGB. Проверь число успешных операций и конкретные node ID.

## Как объяснять остатки

Каждый старый источник из полного обхода должен иметь число применений, список node ID и причину. В коротком ответе достаточно сводки и характерных ссылок; полный список сохраняй в отдельном доступном отчёте, если объём велик.

Допустимые причины:

| Причина | Что должно быть установлено |
|---|---|
| Kids | Детская тема/компонент или предок; источник не входит в пять разрешённых исключений |
| light | Светлая тема/вариант или предок; источник не входит в пять разрешённых исключений |
| Инстанс | ID инстанса и, когда доступно, ссылка на исходный мастер |
| Вне мастера | Путь до примера, оформления, гайда или контейнера |
| Требует согласования | Конкретные кандидаты и семантическая неоднозначность |
| Нет существующего решения | Проверены и переменные, и стили доступных источников |
| Не проверено | Ошибка/лимит инструмента и точная непроверенная область |

«Это, вероятно, инстансы» без привязки к узлам — не результат аудита. Не скрывай остальные старые стили без префикса Deprecated: перечисляй их отдельно, не присваивая им автоматически статус актуальных или разрешение на замену.

## Лимиты и завершение

Не возвращай полное дерево файла в одном ответе инструмента. Разбей обход по устойчивым node ID, сохраняй результаты вне Figma и объединяй по уникальному ключу применения. В модель возвращай компактные сводки; детальные строки сохраняй без усечения. Усечённый вывод не подтверждает полное покрытие.

После ошибки чтения отметь пакет непроверенным и повтори меньшей порцией. После ошибки записи сначала выясни, что реально изменилось. Не продолжай бесконечно одинаковые запросы: при повторной недоступности инструмента сообщи фактическую границу выполненной работы.

Завершение требует: все корни покрыты, ошибок чтения нет, каждому старому применению назначена доказанная причина, разрешённые однозначные замены сохранены, исключения не получили прямых записей. Сверка Selection colors в UI полезна как независимая проверка, но сама панель без разбора слоёв не определяет допустимость массовой замены.
