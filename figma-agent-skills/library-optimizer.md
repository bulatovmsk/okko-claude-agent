# Skill: аудит и оптимизация Figma-библиотеки Okko

## Когда применять

Используй для порядка страниц и Assets, naming, lifecycle, descriptions и необходимости Sections. Не применяй к внутреннему устройству компонента или продуктовому экрану.

## Сначала аудит

1. Определи роль каждой страницы: guideline, public components, product/templates, draft/WIP/deprecated.
2. Зафиксируй IDs, родителей, координаты, размеры, variants и public properties затрагиваемых нод.
3. Подготовь полную предлагаемую карту страниц и список переименований.
4. Не изменяй файл, пока пользователь явно не согласовал запись.

## Правила структуры

- Группируй страницы по сценарию использования, а не автоматически по алфавиту.
- Нумеруй только страницы или папки, влияющие на порядок Assets; номер определяй по живой структуре.
- Не добавляй номера в имена `COMPONENT` и `COMPONENT_SET`.
- Для компонентов предпочитай плоское имя `Group - Component`; не создавай глубокую `/`-иерархию без согласования.
- Sections нужны для чтения холста, а не для организации Assets. Не добавляй их на маленькую страницу без пользы.
- Lifecycle использует принятые маркеры: ready 🟢, design-only 🔵, WIP 🟡, planned ⚪, deprecated 🔴.
- Description должна содержать назначение, ограничения, платформу и короткие поисковые термины.

## Безопасная запись

- Naming, descriptions и статусы исправляй отдельно от structural refactor.
- При reparenting сохраняй абсолютные координаты и проверяй их после записи.
- Не меняй variants, properties, размеры, auto layout, токены и поведение реализованного компонента без отдельного согласования.
- Не выноси системные iOS-референсы в другую библиотеку без решения владельца.

## Результат

Перечисли изменённые страницы и component sets, сохранённые инварианты и решения, которые ещё требуют согласования. После записи проверь Assets, вложенность и визуальный результат.
