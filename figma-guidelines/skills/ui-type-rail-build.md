# UI Type Rail Build

Выполняй workflow в Figma Design, создавая редактируемые связанные компоненты. Сначала исследуй текущий файл, затем доступные внешние зависимости. Правила доступны через Guidelines подключённой библиотеки или резервный справочник внутри этого skill.

## Работа в фича-макете и перенос в библиотеку

По умолчанию собирай Rail в текущем фича-файле рядом с концептом или в указанной дизайнером области. Подключённая UI Type — источник опубликованных Rail Card, Rail Heading, Rail Example, запчастей, переменных и Guidelines. Наличие концепта в продуктовом файле не требует переноса работы в библиотеку.

1. Проверь реальные опубликованные зависимости, доступные через подключённую UI Type. Rail Card импортируй как шаблон для самостоятельной карточки UI Type: detach только внешнего экземпляра, затем собственный мастер с вариантами размеров. Heading, платформенные базы и совместимые запчасти сохраняй связанными. Внутри библиотеки используй доступные локальные мастера. Не отвязывай базы ради обхода недоступной зависимости. Если транзитивная зависимость доступна через экземпляр, дополнительное подключение платформенной библиотеки не требуется. Если для нового элемента нужен недоступный мастер, назови конкретную библиотеку и продолжай независимую работу.
2. Используй существующий UI Type или экземпляр Rail Example как отправную точку. Внешний экземпляр Rail Example разрешено detach. Для карточки используй собственный мастер UI Type без вложенной универсальной Rail Card, с восстановленными boolean-свойствами и обычными FRAME Overlay/Caption. Heading и вложенные платформенные базы сохраняют связи. Создай локальный Rail, набор карточек по размерам и только необходимые запчасти. Исходный библиотечный мастер не меняй ради фичи.
3. Выполни запрошенный платформенный охват. Например, запрос «Web» означает шесть Web-брейкпойнтов, без автоматической сборки iOS и Android. Для общего запроса без указания платформ сохраняется полный охват 5/3/6. Подготовь проверку в этом же фича-файле.
4. Дизайнер дорабатывает композицию, содержимое и размеры локального Rail. При повторном запуске сохраняй его изменения и исправляй только запрошенное. Связи с библиотечными базами и привязки переменных сохраняются.
5. По отдельному запросу перенеси согласованный UI Type в библиотеку и адаптируй под оставшиеся платформы. Перед переносом проверь конфликты имён, существующие мастера, запчасти и ссылки из фича-файла. Переноси Rail и уникальные запчасти вместе через поддерживаемый Figma перенос компонентов между файлами, сохраняя идентичность и связи. Если такой перенос недоступен инструменту, укажи нужное ручное действие, а не создавай молча дубликат. После переноса проверь собственные мастера карточек, вложенные зависимости, boolean-связи, темы, сохранённые исходные слоты (если есть) и экземпляры исходного файла. Публикация и обновление экземпляров — отдельные явные действия, статус каждого сообщай.

Текущий навык собирает Rail. Для Android Grid сверяй соответствующий мастер на странице <тип> Grid в UI Type и проверяй зазоры по конкретному исходному набору. TV использует отдельную библиотеку и свои правила.

## До записи

2. Найди компоненты сначала в текущем файле и его доступных страницах. Если здесь находятся реальные локальные мастера Rail Card нужных платформ и Rail Heading, используй их без требования подключить этот же файл через Libraries. Это применимо и к рабочей ветке библиотеки; одинаковое название само по себе не доказывает наличие компонентов. Если нужных локальных мастеров нет, ищи во внешних подключённых библиотеках и запрашивай подключение только действительно недоступной зависимости.    Прочитай доступные Guidelines библиотеки. Если они не попали в контекст, используй резервный справочник в конце этого skill; не останавливай всю сборку только из-за отсутствия шести файлов в контексте. Явные актуальные указания дизайнера и подтверждённые новые правила имеют приоритет над резервной версией.
3. Найди фактические Rail Card нужных платформ, общий Rail Heading и подходящие запчасти. Базовые элементы берутся из Lib-iOS, Lib-Android-Mobile и Lib-Web или подтверждённой общей библиотеки. Существующие вложенные экземпляры с корректными связями сохраняй; не требуй повторного импорта уже имеющейся детали. Если нужен отсутствующий базовый компонент и его импорт недоступен, назови конкретную зависимость; не подменяй нарисованной копией. Пока она недоступна, продолжай независимые платформы и элементы.
4. Зафиксируй заданное дизайнером, унаследованные правила и допущения. Составь соответствие элемент → мастер → слой/свойство → источник размера.

## Сборка

5. Выбери фиксированную пропорцию или Custom по правилу 15% из Guidelines. Другую структуру собери кастомно из существующих базовых элементов. Для нового размера предложи радиус по минимальной стороне; явный выбор дизайнера имеет приоритет.
6. Подготовь три набора с полным покрытием 5 iOS, 3 Android, 6 Web, включая Desktop, если пользователь не ограничил охват. На iOS сохраняй утверждённые фиксированные размеры, на Android используй сеточную модель, на Web — его формулу и breakpoint. Не применяй одну формулу ко всем платформам.
7. Собери Rail Heading, карусель и карточки через Auto Layout и собственные мастера по components.md. Rail Card — шаблон: detach внешней оболочки, без вложенной универсальной базы. Overlay/Caption — FRAME, не SLOT. Восстанови Small/Large/Indicator/Rich label, Skeleton, Card caption, Cover elements; свяжи видимость на всех вариантах и проверь включение/выключение. Привяжи внутренние padding и gap карточек к семантическим переменным `spacing/*` из Tokens Web&Mobile. Сохрани связи вложенных баз, переменные, стили и техническое имя Cover. Проверь повторное наследование ширины и внутренних правок от собственного мастера, отсутствие непреднамеренных width/height overrides. Тексты/картинки отдельных карточек остаются overrides контента; служебные элементы не заменяй карточками. На каждую обложку всегда ставь существующую дефолтную картинку-плейсхолдер библиотеки, включая Custom. У Carousel clipsContent=false; не экспонируй внутренние экземпляры в Nested instances без явного запроса. Используй существующие детали; недостающие уникальные мастера размести рядом с Rail.
8. Оформи страницу и имена по Guidelines: страница `<тип> Rail`, компоненты `Rail <тип> 🍎 iOS`, `Rail <тип> 🤖 Android`, `Rail <тип> 🌐 Web`, мастера в ряд, без секций-обёрток. Все запчасти публикуются с префиксом x / ; для наполнения слота добавляй Slot в имя. Не скрывай запчасти через _. При пересборке сохрани пригодные ID и явные дизайнерские настройки.
9. Не создавай новых токенов, переменных, aliases или коллекций. Используй только доступные существующие привязки. Не меняй исходники платформенных Rail и не публикуй библиотеку без отдельного указания.

10. Подготовь платформенные проверочные секции с экранными фреймами и включёнными существующими локальными сетками по layouts.md; общий Preview без устройств не создавай. Найденные ошибки сообщай без автоматического исправления. Проверь все целевые варианты, происхождение instances, размеры обложки отдельно от подписи, Rail Gap, привязки и значения внутренних отступов, радиусы и темы, слоты, видимость, текст и намеренную обрезку. При переносе сравни все карточки и скрытые слои исходника.
11. Дай ссылки на готовые наборы и проверочные секции, покрытие платформ, использованные размеры/расчётные основания и существенные допущения. Отличай структурную, визуальную проверку и дизайнерское утверждение. Известные ограничения не отмечай выполненными.
12. Передай полноценную основу для донастройки дизайнером. Для отдельно запрошенного тестового запуска используй согласованную тестовую область, сохрани исходный концепт и критерии проверки. Не называй тест пройденным до проверки фактического результата.

## Роль инструмента

Создай полноценную редактируемую компонентную основу по концепту продуктового дизайнера. Концепт может быть текстом, вайрфреймом из прямоугольников, изображением или подробным дизайном. Дизайнер оценивает результат, донастраивает его и принимает окончательное решение.

Низкая детализация концепта не требует рисовать компоненты с нуля. Выбери существующие компоненты и платформенные стили. Не добавляй неуказанные действия и контентные поля ради декоративной полноты.

При пересборке сохраняй явные дизайнерские настройки. Отличие от рекомендательной шкалы радиусов не является ошибкой. Не сбрасывай донастройку к исходной рекомендации.

## Решения до сборки

Сначала проверь компоненты на доступных страницах текущего файла. Если локальные мастера Rail Card и Rail Heading уже здесь, используй их напрямую; подключать тот же файл как внешнюю библиотеку не требуется для поиска этих мастеров. Проверяй реальные узлы и связи, не одно название файла. Ветка или копия с другим file key допустима, когда дизайнер задал её как рабочую и нужные мастера доступны. Внешнее подключение запрашивается только для отсутствующей зависимости.

Определи назначение Rail, повторяемую единицу (карточка или многорядная колонка), контент, действия, подписи, ряды, пропорции и состояния. Отличай заданное дизайнером от унаследованного библиотечного правила и собственного допущения.

Составь соответствие: элемент концепта → реальный мастер → платформа → слой/свойство → источник размера. Для нового типа используй ближайшее проверенное семейство как источник геометрии только при совпадении композиции. Укажи, какие параметры наследуются.

Неизвестные N, span или размер нового iOS-типа не выдавай за утверждённые. Если несколько трактовок меняют смысл или композицию, уточни выбор; независимую понятную часть продолжай. Не требуй подробного макета только ради наличия всех пиксельных значений.

## Кто отвечает за карточку

Библиотечная Rail Card задаёт шаблон. Агент создаёт самостоятельный мастер карточки конкретного UI Type с вариантами размеров, без вложенной универсальной Rail Card и без новых слотов. Дизайнер правит этот мастер; карусель использует его связанные экземпляры. Общие переключатели восстанавливаются после detach. Полный порядок, схема, примеры, проверки и исключения — в components.md. Изменения структуры шаблона не приходят автоматически; существующие токены и вложенные базы продолжают обновляться.

# Okko UI Type — переменные и визуальные настройки

## Обязательные привязки

Используй существующие переменные и стили; импорт опубликованной переменной разрешён. Новые токены, переменные, aliases и коллекции не создавай. Совпадение чисел не заменяет привязку.

Цвета и типографику наследуй от реальных компонентов целевой платформы и их семантических стилей/переменных. Не снимай HEX и шрифт с вайрфрейма как готовое правило. Не выдумывай пути цветовых или типографических токенов. Переключение темы должно сохранять семантическую роль, а не текущий цвет.

Межкарточные интервалы — локальные переменные UI Type:
- rail/gap-horizontal/phone: 6;
- rail/gap-horizontal/tablet: 8;
- rail/gap-horizontal/desktop: 10.

На Web 1440 используется tablet=8 при Device=Desktop. Значение в формуле и фактический gap должны соответствовать одному токену.

В Android межколонник guides также привязан к rail/gap-horizontal/phone=6 и tablet=8; отдельные spacing/150 и spacing/200 здесь не используются.

Screen padding берётся из семейства целевой платформы, перечисленного в platforms.md. Не заменяй его совпадающим числом из другой платформы.

## Радиусы Rail Card

Выбирай радиус карточки/обложки исключительно через rail/card/radius/*. Сохраняй привязку всех соответствующих углов Cover собственного мастера карточки после detach шаблона. Вложенные кнопки и лейблы сохраняют собственные платформенные радиусы.

Для нового Rail предлагается рекомендательная beta-шкала:
S = min(ширина, высота скругляемой обложки).
Подпись под обложкой не входит в S. У полностью кастомной карточки с единым скругляемым контейнером измеряется именно этот контейнер; обозначь выбранную область.

| S, px | rail/card/radius/ | Main | Meta |
|---|---|---:|---:|
| S < 106 | 400 | 8 | 12 |
| 106 ≤ S < 192 | 450 | 10 | 16 |
| 192 ≤ S < 236 | 500 | 12 | 20 |
| 236 ≤ S < 252 | 600 | 14 | 20 |
| 252 ≤ S < 336 | 700 | 16 | 24 |
| 336 ≤ S < 528 | 800 | 20 | 28 |
| S ≥ 528 | 900 | 24 | 36 |

При точном пороге выбирается следующая ступень; S не округляется. Назначается идентичность токена, а не число Main. Например, уровень 500 сохраняется в Meta, где его значение другое. Значения проверены 16 ноября 2026, при сборке читай актуальные переменные.

Это ориентир первоначального выбора, не абсолютная норма: текущие Rail не подчиняются одной монотонной формуле. Дизайнер может выбрать другую ступень. Сохраняй его выбор при пересборке; отличие от шкалы не ошибка.

Circle сохраняет круглую геометрию и исключён из шкалы. Не применяй произвольный radius к кругу. Правило шкалы относится и к Shape=Custom.

В проверенном Rail Card iOS отдельного свойства Radius нет. Не пытайся установить несуществующий prop и не обещай автоматический пересчёт при resize. Выбор и привязку выполняет агент. Если вложенный Cover недоступен для переопределения, сообщи ограничение и проверь собственный мастер карточки. В новой сборке внешний экземпляр шаблона уже detach; Heading и платформенные базы не отсоединяй, общий библиотечный мастер не меняй ради одного Rail.

## Внутренние отступы карточки

Привязывай внутренние отступы карточки к существующим семантическим переменным `spacing/*` из библиотеки **Tokens Web&Mobile**. Это относится к padding и Auto Layout gap внутри карточки, включая Overlay, Caption, группы лейблов и кастомный контент. При пересборке подбирай токен, сохраняющий утверждённый размер отступа в нужном режиме. Межкарточный зазор остаётся на `rail/gap-horizontal/*`.

Если подходящего токена нет или он недоступен, сохрани размер исходника и укажи слой, свойство и значение без привязки. Новые переменные не создавай. Для внутренних отступов не используй токены радиуса или Rail Gap, даже если значения совпадают. Проверь привязки и вычисленные значения для каждого размера карточки.

В части iOS Rail ещё встречаются внешние rail/card/radius/600, /700, /800. Их Main/Meta-значения совпадали с локальными, но внешняя коллекция дополнительно имела Kids. При пересборке не меняй источник автоматически только из-за совпадения чисел.

# Okko UI Type — выбор компонентов

## Источники и зависимости

Rail Card iOS, Rail Card Android и Rail Card Web находятся в библиотеке UI Type на странице Rail Shared. Используй экземпляр соответствующей платформы как шаблон собственной карточки UI Type; внешняя оболочка отсоединяется, вложенные платформенные базы сохраняют связи. Rail Heading — общий компонент этой же библиотеки.

При сборке внутри самой UI Type или её рабочей ветки сначала ищи локальные мастера на всех доступных страницах. Если они найдены, используй их непосредственно. Отсутствие текущего файла в списке подключённых внешних Libraries не доказывает отсутствие локальных компонентов. Не запрашивай подключение этого же файла до проверки его содержимого.

Label, Rich Label, кнопки и другие базовые элементы подгружай из Lib-iOS, Lib-Android-Mobile или Lib-Web, либо подтверждённой общей библиотеки. Проверяй реальный мастер, не только похожее имя. Не detach и не рисуй копию недоступного компонента. Если зависимости нет среди доступных библиотек, сообщи, какую библиотеку нужно подключить; продолжай независимую работу.

Уникальные детали конкретного Rail создавай локально рядом с ним, только когда подходящей детали ещё нет. Совместимые подписи, оверлеи, прогресс и другие запчасти переиспользуй, проверив типографику, состояния, токены и базовые зависимости. Для совместимых запчастей разница только в ширине не требует нового мастера. Рабочая карточка UI Type при этом получает варианты размеров для независимого редактирования.

## Форма и правило 15%

Стандартные Shape: Horizontal 16:9, Vertical 2:3, Square 1:1, Circle 1:1. Пропорция относится к обложке без подписи.

Перед выбором Custom вычисли:
rConcept = ширина обложки концепта / её высота
rFixed = ширина / высота подходящей фиксированной пропорции
D = abs(rConcept - rFixed) / rFixed × 100%.

Сравни доступные фиксированные варианты, совместимые по структуре и форме. Выбери вариант с минимальным D:
- D ≤ 15%: используй фиксированную пропорцию;
- D > 15% от всех подходящих фиксированных вариантов: по умолчанию используй Shape=Custom, сохранив пропорцию концепта.

При ровно 15% выбирается фиксированная пропорция. До сравнения не округляй D. Например, 1,6 относительно 16:9 отклоняется на 10% — выбирается 16:9. Пропорция 2,1 отличается примерно на 18,125% — выбирается Custom, если другой подходящий фиксированный вариант не ближе.

Равное 1:1 у Circle и Square не означает взаимозаменяемости: сохраняй заданную форму. Явная последующая настройка дизайнера имеет приоритет над первоначальным автоматическим выбором.

Если структура Rail Card подходит, нестандартная пропорция решается через Custom. Если нужна иная структура или поведение, создай полноценную кастомную локальную карточку из подходящих базовых компонентов. Нестандартная пропорция сама по себе не причина пропускать UI Type.

## Наполнение и высота собственной карточки

В новой рабочей карточке Overlay и Caption — обычные FRAME с конкретным содержимым, без SLOT-свойств. После detach восстанови семь boolean-связей; встроенные лейблы, индикаторы и Skeleton не дублируй. При точном переносе уже существующего компонента с настоящими SLOT (например, Featured Meta) сохраняй его слоты, настройки и картинки: это отдельный контракт, не новая сборка по шаблону.

У Shape=Custom меняются ширина и полная высота экземпляра. Cover занимает доступное место, подпись добавляет собственную высоту. Если нужна заданная высота обложки, общая высота включает подпись и применимые интервалы. Прямое изменение вложенного Cover может быть ограничено экземпляром — проверяй фактический результат.

Для автоматической подстановки изображений сохраняй техническое имя Cover. Пропорцию проверяй по скругляемой обложке, не по полному экземпляру с подписью.

## Шапка

Используй общий Rail Heading, Type=Base или Rich, с подходящим Device. Phone/Tablet одинаковы по платформам; отдельные платформенные копии не нужны.

При проверке Rail Heading переключи `Show arrow` на связанном экземпляре на ширине целевого устройства. Заголовок остаётся у левого края в обоих состояниях, видимая стрелка Base Phone/Tablet — у правого. В Base Tablet используй `Content = Fill container` и `Title = Hug contents`: при скрытой стрелке контейнер с `Space between` и `Content = Hug contents` центрирует заголовок.

У Desktop уже предусмотрены более крупные типографика/изображения, правая стрелка шапки скрыта. Стрелка перехода в шапке и управление прокруткой карусели — разные элементы: скрытая стрелка не отменяет навигацию карусели.

## Перенос существующего Rail

Проверяй каждую исходную карточку каждого варианта, скрытые потомки и overrides. Сохраняй состав и исходную видимость, а отсутствующие уникальные детали добавляй в Overlay/Caption собственного мастера; существующие исходные слоты сохраняй при точном переносе. Обход только видимых карточек недостаточен.

Исходные Rail в платформенных библиотеках используются для чтения; сборка в UI Type не даёт разрешения редактировать или удалять исходники. WIP не включается без расширения задачи. Состав текущей ветки проверяй в живой Figma.

## Пример Rail и дефолтная обложка

На Rail Shared собраны базовые Card и Heading, Rail Example, общие запчасти и примеры сеток. Rail Example — пример композиции: его экземпляр можно detach для собственной сборки, сохраняя Heading и платформенные базы. Карточки переводятся на собственные мастера UI Type через разрешённый detach внешней оболочки Rail Card; вложенные базовые компоненты не detach.

При сборке по концепту всегда ставь на каждую обложку существующую дефолтную картинку-плейсхолдер библиотеки, на всех платформах, включая Custom и полностью кастомные карточки. Не заменяй её серой заливкой, пустой обложкой или контентной картинкой из концепта. Переноси текст и оверлеи независимо от картинки. Проверяй фактический плейсхолдер во всех обложках; Skeleton — отдельное состояние. Если библиотечная картинка недоступна, сообщи об ограничении, не придумывай и не генерируй замену. При аудите существующих UI Type изображения автоматически не меняй.

В конечном Rail не экспонируй Heading, карточки и технические вложенные экземпляры в Nested instances без явного запроса. Связи с мастерами и полезные свойства Rail, например Show heading, сохраняются.

Решение проверено на Continue 18 ноября 2026. Применяется по умолчанию к новым сборкам и явно запрошенной пересборке. Не мигрируй остальные существующие UI Type автоматически. Особые исходные компоненты, например Featured Meta с настоящими слотами, сохраняют свой контракт при точном переносе.

## Зачем и как устроено

Библиотечная Rail Card — шаблон правильного устройства, состояний и привязок. Рабочая карточка конкретного UI Type — самостоятельный локальный мастер. В карусели стоят его экземпляры. Дизайнер меняет один мастер нужного размера, и изменения применяются ко всему этому варианту Rail.

```text
Rail <тип> 🌐 Web                       x / Rail <тип> Card Web
├── Rail Heading → связанный мастер    ├── breakpoint=375
└── Carousel                          │   ├── Cover
    ├── Card 01 ──────────────────────┤   │   ├── Cover (изображение)
    ├── Card 02 → тот же мастер       │   │   ├── Overlay (FRAME)
    └── Card 03 → тот же мастер       │   │   ├── общие лейблы
                                      │   │   └── Skeleton
                                      │   └── Caption (FRAME)
                                      └── остальные размеры
```

В рабочем мастере нет вложенного экземпляра универсальной Rail Card. Не создавай схему «собственная карточка → всё ещё связанная Rail Card». Библиотечные Heading, Label, Rich Label, Indicator, кнопки и совместимые запчасти остаются связанными. Detach относится к внешнему экземпляру шаблона карточки, не ко всем вложенным компонентам и не к библиотечному мастеру.

На каждую платформу — набор `x / Rail <тип> Card iOS / Android / Web`. Размеры — варианты Device/breakpoint внутри набора, а не отдельный мастер для каждого элемента списка. Разные размеры, которые дизайнер должен редактировать независимо, получают отдельные варианты, даже если используют одно Phone/Tablet-основание. Только подтверждённые одинаковые размеры и поведение можно объединять. В многорядной карусели колонка содержит экземпляры карточек, а не независимые нарисованные копии.

Square Small 1 Story и 2 Story используют общие наборы `x / Rail Square Small Card` по платформам. Мастера находятся на Square Small 2 Story Rail. На Web сохрани варианты `Layout` внутри общего набора, включая вариант с подписью. Для проверки 1 Story ищи мастер по связи экземпляра, даже если он на другой странице.

## Сборка

1. Найди фактический платформенный шаблон и прочитай его свойства, связи, скрытые слои, токены, min/max и содержимое. Разреши зависимости до detach. Если карточка несовместима с шаблоном, собери собственную композицию из подходящих платформенных баз; не подгоняй исходник под Rail Card.
2. Настрой экземпляр шаблона под тип, задай утверждённые/рассчитанные размеры. Сделай detach только его внешней оболочки и создай из результата локальный компонент. Не переименовывай и не меняй исходный библиотечный мастер. Геометрия Cover измеряется отдельно от Caption.
3. Overlay и Caption в новой рабочей карточке — обычные FRAME с Auto Layout и конкретным наполнением. Слоты и SLOT-свойства по умолчанию не создаются: необходимость в подстановке произвольной композиции здесь заменена редактированием своего мастера. Сохраняй структуру и имя технического изображения Cover, пропорции, содержимое, ограничения и библиотечные привязки. Наличие заполненного FRAME не делает его SLOT.

   При разборе старого шаблона распознавай `↳ Добавить подпись` как `Caption`, а `↳ Добавить элементы` как `Overlay` (с префиксом `↳` или без него). После detach используй имена `Caption` и `Overlay` для обычных FRAME самостоятельной карточки. Сверяй роль по положению слоя и связи видимости. Сохраняй свойства `Card caption` и `Cover elements` и их привязки. Имена настоящих SLOT в исходных компонентах сохраняй.
4. Восстанови общие свойства по таблице ниже. Detach и createComponentFromNode не гарантируют сохранения свойств: в проверке Continue все семь boolean-связей пришлось создать заново. Свойства добавляются на COMPONENT_SET, ссылки на видимость — на соответствующие слои каждого варианта.
5. Создай экземпляры своего мастера в Carousel. Не оставляй прямые экземпляры универсальной Rail Card, независимые FRAME или собственный мастер на каждую карточку. Изображения и тексты отдельных карточек переноси как overrides содержимого; размеры и общая структура должны наследоваться от мастера.
6. У нового экземпляра сначала проверь фактический размер. Не вызывай resize с теми же размерами «для надёжности»: этим можно создать width/height overrides и сломать общий ресайз. При миграции предпочтительны новые экземпляры мастера с восстановленным содержимым. Если надо очистить overrides, сначала сохрани все индивидуальные настройки; removeOverrides без восстановления контента запрещён.
7. Сохрани отдельные служебные элементы карусели: «Смотреть всё», навигацию, рекламные вставки. Они не становятся экземплярами карточки контента только потому, что тоже имеют тип INSTANCE. Отличай их по реальному мастеру и назначению. В Continue Web терминальные элементы были восстановлены отдельно.

## Семь обязательных переключателей стандартной карточки

| Свойство | Какой слой включает | Значение по умолчанию |
|---|---|---|
| Small label | группа маленьких лейблов в Labels / padding | сохранить состояние концепта/исходника |
| Large label | встроенный крупный лейбл | сохранить состояние концепта/исходника |
| Indicator label | встроенный индикатор | сохранить состояние концепта/исходника |
| Rich label | встроенный Rich label | сохранить состояние концепта/исходника |
| Skeleton | слой поверх Cover со стилем `color/fill/technical/skeleton` | обычно false; исходник имеет приоритет |
| Card caption | FRAME Caption | сохранить видимость подписи |
| Cover elements | FRAME Overlay | сохранить видимость элементов обложки |

Скелетон состоит из двух заливок Okko Head Library. На FRAME Skeleton привяжи сплошную подложку к существующей переменной `color/fill/technical/placeholder`. Сверху помести слой с paint style `color/fill/technical/skeleton`, растянутый на весь фрейм. Подложка закрывает изображение, а полупрозрачный градиент сохраняет исходный вид. Boolean Skeleton управляет видимостью всего фрейма. При замене сохраняй размеры, скругление и порядок слоёв. Используй обычные слои без библиотечного экземпляра Skeleton View.

В принятом Continue: четыре лейбла и Skeleton выключены, Caption и Cover elements включены. Это пример, не новые глобальные дефолты. Привязывай Rich label именно к общему встроенному слою, а не к случайному Rich label внутри уникального Overlay. Не заходи в чужой INSTANCE ради перепривязки его внутренних свойств. В собственном кастомном типе переноси применимые состояния и явно обозначай отсутствующие возможности; не добавляй пустой переключатель, который ничего не делает.

Нельзя ограничиться названием свойства: `componentPropertyReferences.visible` должен указывать на реальный boolean-key. Нельзя читать/создавать componentPropertyDefinitions на отдельном variant-компоненте: владелец — набор. Проверь фактические boolean-значения на тестовом экземпляре каждого варианта, включая скрытые потомки (`skipInvisibleInstanceChildren=false` при доступном Plugin API).

Device/breakpoint сохраняются. Shape универсального шаблона не переносится как фиктивный список, если готовый UI Type поддерживает одну форму: исходный выбор пропорции остаётся решением сборки. Создавай дополнительные варианты Shape/состояния только при реальном поведении типа или явном запросе. Другие применимые TEXT/INSTANCE_SWAP-свойства исходника сохраняй или восстанавливай с действующими связями; отсутствие таких свойств в конкретном шаблоне не повод выдумывать их. Полезные свойства карточки не означают автоматическое экспонирование всех её вложенных экземпляров в конечном Rail.

## Проверки перед передачей

- Каждый элемент контента в каждом Carousel ссылается на нужный собственный мастер. Нет слоя универсальной Rail Card между мастером и Cover. Caption/Overlay — FRAME; новые SLOT-свойства отсутствуют.
- Все семь переключателей стандартной карточки работают на каждом варианте: включить → проверить слой, выключить → проверить слой. Проверь, что исходный внешний вид до добавления свойств и после него совпадает.
- При пересборке существующего специализированного Rail сохраняй размеры карточек, видимый и скрытый контент, индивидуальные настройки экземпляров и связи базовых кнопок, лейблов и логотипов. После detach или замены мастера сверяй тексты, состояния и подписи вложенных кнопок, а также унаследованные размеры. Если исходник даёт один планшетный вариант на два проверочных экрана Android, используй его размеры на обоих и явно укажи принятое решение.
- Проверь привязку внутренних padding и gap, включая Overlay, Caption и группы лейблов, к семантическим `spacing/*` из Tokens Web&Mobile. Сверь вычисленные отступы с исходником на каждом размере.
- На временных связанных экземплярах измени ширину мастера дважды и проверь обе реакции всех карточек. Проверь также внутренний отступ/компоновку. Однократный успешный ресайз не доказывает дальнейшее наследование. Не оставляй тестовые изменения и не создавай overrides размеров проверочных экземпляров для маскировки ошибки.
- В рабочих экземплярах нет непреднамеренных root width/height overrides. Индивидуальные картинки, тексты, состояния, скрытые элементы и служебные карточки сохранены. Наличие override name или содержимого допустимо.
- Углы Cover по-прежнему связаны с существующими rail/card/radius/*, gap — с существующими Rail Gap. Проверь min/max, FILL/HUG/FIXED, ограничения пропорции и темы. Новых дизайн-переменных не создавай.
- При переносе изображений, в том числе внутри сохранённых исходных слотов, проверь не только геометрию, но и реальную IMAGE-заливку, наличие байтов в целевом файле, FIT/FILL и imageTransform. Совпавшие пустые заливки импортированной копии не доказывают совпадение с живым Android/iOS/Web-оригиналом.

Проверку наследования выполняй на изолированных копиях либо сохраняй и восстанавливай состояние рабочих объектов; после теста ещё раз проверь отсутствие overrides размеров. Сборку и исправление незавершённой реализации отделяй от финального дизайнерского аудита: обнаруженные при финальной проверке расхождения показывай с устройством, узлом, ожидаемым/фактическим значением и предложением исправления.

## Граница применения и пример

Ради изменения одного UI Type не отсоединяй Heading, Label, кнопки и остальные базы. Структурные обновления универсальной Rail Card не попадут в самостоятельную карточку автоматически; токены и связанные вложенные базы продолжат обновляться. Это осознанный компромисс ради самостоятельной работы продуктового дизайнера.

При точном переносе существующего компонента с настоящими SLOT (например, Featured Meta) сохраняй SLOT, slotSettings, min/max, содержимое и свойства, а не применяй правило FRAME задним числом. Новая архитектура не разрешает массово переделывать существующие компоненты. Явный запрос сохранить кастомную композицию без отдельного компонента карточки также имеет приоритет.

Это пример архитектуры, не универсальный источник размеров других типов. # Okko UI Type — структура, адаптация и сетки

## Организация мастеров

Страницы называй `<тип> Rail`, например `Vertical Rail`. Сортируй их по названию типа внутри существующих групп и сохраняй разделители. Для Grid используется формат `<тип> Grid`. Эмодзи ставь только в именах основных платформенных UI Type, включая Grid, Featured и Banner. Имена страниц, базовых компонентов и запчастей сохраняй без платформенных эмодзи. Основные компоненты `Rail <тип> 🍎 iOS`, `Rail <тип> 🤖 Android`, `Rail <тип> 🌐 Web`. Платформы стоят в ряд слева направо iOS → Android → Web.

Мастера находятся прямо на странице без SECTION и лишних внешних контейнеров. Запчасти — рядом с соответствующим Rail. Общие детали хранятся один раз. Проверка размещается в отдельных платформенных секциях с экранными фреймами; запрет секций-обёрток относится к мастерам.

Все запчасти, в том числе общие, называются `x / Rail <тип> <роль> [платформа] [размер]` и публикуются в группе x. Для наполнения слотов добавляй Slot: `x / Rail <тип> Slot <роль> [платформа] [размер]`, например x / Rail Media Slot Overlay Phone. Не скрывай запчасти через `_`. Основные Rail, базовые Card и Heading остаются без x / . Не добавляй префикс UI Type и длинные цепочки через дроби: Grid — отдельный тип, а принадлежность к UI Type уже задана библиотекой.

## Внутренняя компоновка

Основной каркас — Rail Heading и Carousel в вертикальном Auto Layout. Внутри Carousel карточки или колонки располагаются горизонтально. Row/Column сохраняются там, где они выполняют функцию. Base Rail и одноэлементные обёртки без роли не нужны.

Шапка растягивается по видимой ширине. Скрытая шапка не оставляет пустой интервал. Высота Rail учитывает реальные видимые элементы, подписи и дополнительные блоки.

Карточкам задаётся рассчитанная ширина. Fill у всего списка не должен перераспределять ширину между всеми экземплярами и менять заданную плотность. Оверлеи привязываются к Cover; подпись находится ниже него.

Двухрядный Rail: различай карточку и повторяемую колонку. В формулах N относится к горизонтальной единице, а не сумме карточек двух рядов. Вертикальный gap проверяется отдельно от горизонтального.

У Carousel всегда clipsContent=false. Переполнение ограничивает внешний экранный фрейм проверки с clipsContent=true. Скругление и clipping Cover сохраняются независимо. Проверяй скрытые состояния и длинный текст, не только исходный экран.

## Области и ресайз

При добавлении UI Type в основную библиотеку обнови каталог UI Type на странице Structure (2300:26048). Добавь одну плитку на тип с узнаваемым связанным экземпляром карточки одной платформы и ссылкой на актуальный мастер в этой библиотеке. При добавлении платформы к существующему типу переиспользуй плитку. Для похожих карточек можно подписать отличие композиции, например число рядов.

Полная ширина экрана, видимая ширина Rail и область расчёта карточек — разные величины. Не вычитай screen padding повторно из уже ограниченного родителем контейнера.

На iOS сохраняются утверждённые фиксированные размеры. Android адаптируется по сетке и образцам. Web имеет шесть опорных вариантов; Auto Layout сам по себе не реализует формулу N при любом resize. Поведение между опорными ширинами не выдумывай: возьми подтверждённый пример или обозначь допущение.

## Нативные Layout Guide styles

Стиль назначается фрейму полной ширины экрана. Колонки STRETCH растягиваются, но стиль не переключается автоматически при изменении ширины.

| Стиль | Размеры | Колонки | Padding | Gutter | Полоса R |
|---|---|---:|---:|---:|---:|
| Web/Mobile (320, 375) | 320, 375 | 12 | 12 | 6 | 36 |
| Web/Tablet (768, 1024) | 768, 1024 | 12 | 32 | 8 | 56 |
| Web/Desktop M (1440) | 1440 | 12 | 56 | 8 | 56 |
| Web/Desktop L (1920) | 1920 | 12 | 72 | 10 | 72 |
| Android/Phone | 360 | 8 | 16 | 6 | нет |
| Android/Tablet | 640, 1024 | 12 | 24 | 8 | нет |

На Web 12 колонок — вспомогательный ориентир, а не замена формулы через N. Красная полоса обозначает полный R от правого края. В Android gutter сетки и межкарточный gap используют одни Rail Gap 6/8; специальная правая полоса не добавляется.

Пары Web Mobile и Tablet используют общие стили. Desktop разделён, поскольку параметры различаются. У примеров нужны подписи breakpoint=320, breakpoint=375, breakpoint=768, breakpoint=1024, breakpoint=1440, breakpoint=1920. Значения включаются и в названия стилей/групп. Пример 440 — только «Пример растяжения», не новый breakpoint.

Существующие iOS/iPhone и iOS/iPad не меняй без отдельного запроса. Если нужный стиль уже существует, переиспользуй его. Новых переменных ради сетки не создавай: Web gutter использует rail/gap-horizontal/*, Android — те же rail/gap-horizontal/phone=6 и tablet=8. Обычный экспорт не показывает нативные guides; проверяй их свойства и отображение в редакторе.

Проверяй реальные gridStyleId, STRETCH, offset, gutter и привязки; показывай результат дизайнеру. Обычный экспорт не показывает guides: visible=true и скриншот экспорта не доказывают видимость сетки в UI. Если показ в UI не подтверждён, сообщи об этом и дай ссылки на секции. Не создавай переменные ради сетки.

Разделяй сборку и проверку. Во время проверки не исправляй найденные ошибки автоматически: сохраняй видимый результат и передавай устройство, ссылку на узел, ожидаемое значение с источником, фактическое значение и предлагаемое исправление. Не маскируй ошибки подбором N, изменением размеров или переопределениями проверочного экземпляра. Отсутствующий вариант явно отмечай на экране, не подменяй другим; это пробел покрытия, а не реализованный вариант. Исправляй по отдельному явному запросу.

## Область размещения

Правила страницы `<тип> Rail` и ряда платформенных мастеров относятся к каталогизации в библиотеке. При работе в фича-файле размещай локальный Rail и проверку рядом с концептом в указанной дизайнером области. Для сеток используй доступные опубликованные стили UI Type: импорт существующего GridStyle разрешён. Если стиль недоступен, сообщи зависимость; не создавай его числовую копию и новые переменные.

## Где дизайнер меняет карточку

Carousel содержит связанные экземпляры x / Rail <тип> Card <платформа>. Для изменения всех карточек выбери мастер нужного Device/breakpoint, а не каждый экземпляр в рейле. Подробная процедура и семь переключателей — в components.md. Нельзя фиксировать размеры всех экземпляров overrides: ширина и общая компоновка наследуются от мастера. «Смотреть всё» и навигация сохраняют собственные компоненты. Весь набор карточек и уникальные запчасти переносится вместе с Rail из фича-файла в библиотеку.

## iOS: фиксированные макеты

| Device самого Rail | Экран | Device Rail Card / Heading |
|---|---|---|
| iPhone 15 | 393 × 852 | Phone |
| iPhone 17 Pro Max | 440 × 956 | Phone |
| iPad Mini 6 | 1133 × 744, Landscape | Tablet |

Для iPhone: L=15, расчётный R=30, G=6.
Для iPad: L=35, расчётный R=50, G=8.
Screen padding: screen-padding/ios/iphone и screen-padding/ios/ipad.

Сохраняй утверждённые фиксированные размеры карточек. Technical JSON используется для проверки, не для автоматического пересчёта:
K = max(0, ceil(N) - 1)
W = (S - L - R - K × G) / N.

S — подтверждённая расчётная база, которая может отличаться от ширины текущего экрана. N>0 задаётся для конкретного типа/устройства и может быть дробным. Не переносить Web N−1 сюда.

Main iPhone 15: утверждённая W=226 соответствует исторической S=390, N=1,5. Текущий экран 393 даёт проверочные 228, но это не основание менять 226. Другие текущие Main: iPhone 17 Pro Max 259,333…; iPad Mini 6 214,333…; iPad 10 222,333…; iPad Pro 13 249,8. Это примеры Main, не размеры всех типов.

Для нового типа предложи черновые фиксированные размеры по каждому устройству, указав источник и допущения; окончательная настройка остаётся дизайнеру. Дополнительные шаблоны iPhone mini и портретных iPad не расширяют обязательный набор автоматически.

В историческом Technical(iOS) встречаются исключение Medium с дополнительным gaps-count−1 и отсутствующая ссылка высоты square-medium. Не исправляй JSON и не распространяй особенности на все типы: сверяй соответствующее семейство.

## Android Mobile: сетка

| Вариант Rail | S | P с каждой стороны | A=S−2P | C колонок | g gutter | G карусели |
|---|---:|---:|---:|---:|---:|---:|
| Phone | 360 | 16 | 328 | 8 | 6 | 6 |
| Tablet P | 640 | 24 | 592 | 12 | 8 | 8 |
| Tablet L | 1024 | 24 | 976 | 12 | 8 | 8 |

Phone Landscape не создаётся: поворот телефона заблокирован. Android-разработка использует dp и адаптируется; не вводи произвольный коэффициент перевода px в dp.

Screen padding: screen-padding/android/phone и screen-padding/android/tablet. У внутренних Rail Card и Heading только Phone/Tablet; сам Rail проверяется на обоих планшетных макетах.

Специального правого расчётного R нет. Для карточек, которые действительно занимают span колонок:
columnWidth = (A - (C - 1) × g) / C
cardWidth = span × columnWidth + (span - 1) × g.

span берётся из концепта или проверенного образца, не угадывается. Не всякая историческая карточка обязана занимать целое число колонок. g и G имеют разные роли, но используют одни существующие Rail Gap: phone=6, tablet=8.

При g=6/8 формула Main даёт Phone span=5 → W=202,75; Tablet L span=3 → W=238; Tablet P span=4 → W=192. Исторические утверждённые W=202/235/189 не пересчитывай автоматически: расхождение фиксируй дизайнеру, общего ceil/floor нет.

Large Phone сохраняет W=289 и обложку 16:9, H=162,5625. Highlights Sport Phone имеет квадратную обложку 328×328 плюс подпись. Circle — 88 Phone и 112 на обоих планшетах; Catalog — 189 на обоих планшетах. Эти примеры не заменяют геометрию других типов.

Старые Technical(Android M) с R=32/72 не являются актуальной моделью. Не подгоняй живые карточки под них.

## Web: опорные breakpoint

| breakpoint | Device | L | R | G | Screen padding токен | rail/gap-horizontal/ |
|---|---|---:|---:|---:|---|---|
| 320 | Phone | 12 | 36 | 6 | screen-padding/web/mobile | phone |
| 375 | Phone | 12 | 36 | 6 | screen-padding/web/mobile | phone |
| 768 | Tablet | 32 | 56 | 8 | screen-padding/web/tablet | tablet |
| 1024 | Tablet | 32 | 56 | 8 | screen-padding/web/tablet | tablet |
| 1440 | Desktop | 56 | 56 | 8 | screen-padding/web/desktop-m | tablet |
| 1920 | Desktop | 72 | 72 | 10 | screen-padding/web/desktop-l | desktop |

Стандартная модель:
A = S - L - R
W = (S - L - R - ((N - 1) × G)) / N.

S — ширина экрана или согласованного внешнего контейнера. N>0 — плотность карточек/колонок в A, а не число instances в карусели. N задаётся для типа и breakpoint до расчёта W. Не восстанавливай N обратной подгонкой под пиксельную ширину концепта ради формального совпадения. Если N не задан и нет подходящего подтверждённого семейства, уточни плотность. При дробном N используется непрерывное N−1, без ceil. Сохраняй точность промежуточных вычислений.

Main 1024: N=4 → W=228.
Main 375: N=5/3 → W=193,8.
Эти N не становятся общими для всех Rail.

Видимая ширина обычного Rail B=S−2L отличается от расчётной A. На 375 B=351, A=327. Шапка/видимая область имеют B, карточки рассчитываются по A.

R — полный отступ от края экрана: screen padding не прибавляется к нему повторно, R не назначается автоматически как paddingRight. На 1440 и 1920 R равен screen padding, дополнительной прибавки 24 нет.

R восстановлен по геометрии стандартных семейств; отдельного подтверждённого Web Technical-токена R не найдено. Highlights/Announces имеют особую геометрию: не навязывай им стандартные R/N без проверки. Старое имя Marketing 1720 не вводит новый breakpoint.

## Высота

После выбора Shape: Horizontal H=W×9/16, Vertical H=W×3/2, Square/Circle H=W. Подпись и её интервалы добавляются отдельно. Историческое округление высоты в Technical JSON не должно незаметно нарушать выбранную пропорцию Rail Card. У кастомной структуры сначала определи повторяемый контейнер; ширина вложенного изображения может отличаться от его ширины.

# Okko UI Type — решения, которых следует избегать

## Вайрфрейм выглядит как набор прямоугольников

Делай: распознай роли и собери из Rail Card, Heading и существующих базовых компонентов.
Не делай: копируй прямоугольники как итоговые карточки и принимай случайный шрифт концепта за платформенный.
Почему: концепт задаёт намерение, библиотека — компонентную реализацию.

## Карточка отличается от стандартной пропорции

Делай: сравни пропорцию обложки с подходящими фиксированными через относительное отклонение. До 15% включительно используй ближайшую фиксированную; выше — Custom.
Не делай: сравнивай только высоты или пропускай UI Type из-за нестандартной пропорции.
Почему: правило относится к отношению W/H; нестандартная структура отдельно решается кастомной карточкой.

## Дизайнер изменил радиус

Делай: сохрани выбранный существующий токен Rail Card.
Не делай: возвращай его к рекомендательной ступени и отмечай осознанное отличие как ошибку.
Почему: шкала помогает начальной сборке, окончательная визуальная настройка принадлежит дизайнеру.

## При смене темы радиус перестал меняться

Делай: проверь variable binding углов скругляемой обложки.
Не делай: назначай число из Main или стороннее семейство радиусов.
Почему: сохранение токена обеспечивает смену значения между режимами.

## У компонента не хватает свойства

Делай: прочитай реальные свойства и возможности переопределения вложенного элемента; назови точное ограничение, если оно есть.
Не делай: вызывай вымышленный Radius prop, detach вложенные платформенные базы или меняй общий мастер для всех ради одного экземпляра.
Почему: удобство операции не оправдывает потерю зависимости или непреднамеренную общую правку.

## Есть похожая запчасть или Skeleton

Делай: переиспользуй совместимую запчасть либо встроенное состояние Rail Card.
Не делай: создавай новую копию для каждого breakpoint, платформы или ширины без реального отличия.
Почему: дубли затрудняют поддержку и дают расхождения.

## Числа совпадают, роли токенов различаются

Делай: используй rail/gap-horizontal/* между карточками и для межколонника Android Rail; это один токен с разными ролями.
Для padding и gap внутри карточки используй семантические `spacing/*` из Tokens Web&Mobile.

Не делай: подставляй Rail Gap или токен скругления как внутренний отступ; для Android не бери старый gutter 8/12 вместо Rail Gap 6/8.
Почему: одинаковая величина не означает одинаковую семантику.

## Проверочная формула расходится с утверждённым iOS

Делай: сохрани размер, запиши входную расчётную базу и расхождение.
Не делай: автоматически меняй Main iPhone 15 с 226 на 228 из-за экрана 393.
Почему: утверждённая геометрия имеет приоритет перед проверочным пересчётом.

## Платформы внешне похожи

Делай: проверь платформенный мастер, базовые зависимости, размеры и модель расчёта.
Не делай: переноси iOS ceil(N)−1 на Web, Web R на Android или считай Desktop 1440 равным gap=10.
Почему: модели и роли Device/токена различаются.

## Карусель видна и кажется правильной

Делай: проверь все исходные карточки, скрытые слои, overrides, подписи и переполнение на всех целевых размерах.
Не делай: объявляй полную проверку по одной видимой карточке или одному скриншоту.
Почему: скрытые возможности и индивидуальный контент могут потеряться при переносе.

## Библиотека успешно собралась

Делай: передай проверенную компонентную основу, различай техническую проверку и дизайнерское утверждение.
Не делай: отмечай недоступные зависимости и неподтверждённые внутренние токены как готовые, публикуй библиотеку или меняй исходники платформ без отдельного указания.
Почему: создание узлов не закрывает известные ограничения и не даёт разрешение на внешнюю публикацию.

## Проверка выявила ошибку

Делай: покажи её на устройстве с локальной сеткой; сообщи ожидаемое, фактическое, узел и предложение.
Не делай: исправляй мастер автоматически, подгоняй N или размеры проверочного экземпляра, скрывай переполнение clipping карусели.
Почему: дизайнер должен видеть фактический результат и принимать решение об исправлении.

## Концепт содержит серую обложку или постер

Делай: поставь существующую дефолтную картинку-плейсхолдер библиотеки на каждую обложку новой сборки.
Не делай: оставляй серую заливку или переноси контентный постер вместо плейсхолдера.
Почему: в компонентной основе по концепту всегда используется дефолтная картинка.

## Дизайнеру приходится менять каждую карточку отдельно

Делай: собственный мастер карточки UI Type по размеру, в Carousel — его экземпляры. Библиотечная Rail Card служит шаблоном и отсоединяется внешней оболочкой.
Не делай: независимые FRAME-карточки, мастер на каждый элемент списка или дополнительную обёртку вокруг всё ещё связанной универсальной Rail Card.

## После detach пропали настройки

Делай: восстанови семь boolean-свойств с действующими связями видимости, проверь все варианты и исходный вид. Новые SLOT не нужны; Overlay и Caption — FRAME.
Не делай: оставляй названия свойств без ссылок на реальные слои или только Device/breakpoint без Skeleton/лейблов. Не добавляй фиктивный Shape без реализованных форм.

## Первый ресайз прошёл, дальнейшие правки не наследуются

Делай: две последовательные правки ширины, проверка внутреннего отступа и root width/height overrides. Индивидуальные тексты и картинки сохрани отдельно.
Не делай: resize каждого экземпляра под мастер и removeOverrides без восстановления содержимого.

## При перепривязке исчезли картинки в слотах исходника

Делай: сравни с живой исходной библиотекой, перенеси оригинальные байты, восстанови IMAGE-заливки, FIT/FILL и imageTransform.
Не делай: сравнивай только две импортированные копии с уже пустыми заливками. Исключение для сохранённых настоящих SLOT не означает, что новой карточке нужны слоты.
